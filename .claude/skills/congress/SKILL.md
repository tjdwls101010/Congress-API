# congress — 국회 의안·의원·회의록

이 스킬의 목적은 조회 자동화가 아니라 **국회를 실제로 아는 상태를 만드는 것**이다. 완결성이 답의 일부인 질문("이 의원이 발의한 법안 전부", "이 법안에 반대표를 던진 의원")은 모집단을 손에 쥐어야만 답할 수 있고, 검색 결과 몇 개로는 대체되지 않는다. **DB는 목적이 아니라 판단의 재료다.**

이 문서의 모든 경로는 `{skill_dir}` — 이 SKILL.md가 있는 디렉터리 — 기준이다.

## 먼저 스키마를 읽어라

```bash
sqlite3 {skill_dir}/CONGRESS.db .schema
```

**함정은 전부 컬럼 주석에 있다.** 이 문서가 스키마를 되풀이하지 않는 이유가 그것이다 — 아래에는 스키마가 답할 수 **없는** 것만 적었다.

값을 추측하지 마라. 위원회명·처리결과·심사상태는 **`SELECT DISTINCT`가 사전이다.** 0건이 나오면 "없다"가 아니라 대개 문자열이 틀린 것인데, 0건은 실패처럼 보이지 않아서 그대로 답이 되어 버린다.

## 판단 원칙

**수집은 완결성을, 조회는 선별성을 목표로 한다.** 두 목적을 섞지 마라 — 수집하면서 "이건 안 쓸 것 같으니 건너뛰자"고 판단하는 순간 완결성이 무너지고, 그 판단이 틀렸을 때 복구할 방법이 없다. 우선순위는 **누락 없음 > 중복 없음 > 속도**다.

## 수집

```bash
uv run {skill_dir}/Scripts/collect.py                 # 정상 경로: 따라잡기
uv run {skill_dir}/Scripts/collect.py --audit-only    # 상태만. 락을 안 잡아 수집 중에도 된다
uv run {skill_dir}/Scripts/collect.py --only meetings
uv run {skill_dir}/Scripts/collect.py --retry all     # 파서를 고친 뒤 상한 도달분 되살리기
```

**하루 1회 자동으로 돌므로 대개 이미 최신이다.** 질문마다 수집부터 돌릴 필요가 없다.

**성공은 종료 코드가 아니라 불변조건이다.** 실행이 stdout에 JSON을 내고, 각 항목은 `pass`·`fail`·`skip`이다. `skip`은 실패가 아니라 **판정할 근거가 없다**는 뜻이다(예: 명부 시드가 없어 총원을 대조할 수 없다).

읽는 법 중 스키마가 말해 주지 않는 것들:

| 값 | 0이 아닐 때의 뜻 |
|---|---|
| `bill_no_gaps` | 그 수만큼 의안이 누락됐다. 산술로 증명되는 유일한 완결성이다 |
| `proposer_count_mismatch` | 원천이 선언한 총원과 저장된 발의자 수가 다르다. **페이징이 샜다는 뜻이다** |
| `stale_details` | 목록이 바뀌었는데 상세를 다시 안 받았다. **갱신이 실제로 도는지를 재는 자리다** |
| `outcome_mismatch` | 저장된 `outcome`이 재계산값과 다르다. 유도 규칙이 바뀌었는데 데이터가 안 따라온 것 |
| `members_missing_party` | 그만큼 **정당별 집계가 틀린다.** 에러가 아니라 조용히 샌다 |
| `votes_without_slug` | 원천이 이름만 주고 slug를 안 준 표다. 이름으로 회수하되 동명이인은 못 푼다 |
| `gone_total` | **실패가 아니다.** 값이 튀면 원천 구조가 바뀌었다는 신호다 |
| `review_status_values` | 원천의 심사상태 값 집합. **못 보던 값이 나오면 `outcome` 규칙을 봐라** |
| `sitting_gaps` | 회의가 빠졌다. **단 국정감사는 이 검사 밖이다**(회기·차수 개념이 없다) |

## SQL로 탐색할 때 — 스키마가 답하지 못하는 것

**FTS가 없다. `LIKE`를 쓴다.** trigram 토크나이저는 3자 미만 질의에 에러 없이 0건을 주는데, 이 도메인에서 가장 자연스러운 질의어가 하필 전부 2자다 — `특검`·`개헌`·`예산`·`AI`. 날짜·위원회·의원 인덱스로 먼저 범위를 좁히면 그 안의 스캔은 빠르다.

**"결국 어떻게 됐나"는 `bills.outcome` 하나로 묻는다.** 예전에는 `review_status`·`decision_result`·`reconsideration_result` 셋을 함께 봐야 했고, 그 조합을 매번 다시 조립하다 보면 조용히 틀린다.

```sql
WHERE outcome = '공포'      -- 법이 된 것
WHERE outcome = '계류'      -- 아직 심사 중인 것
```

값은 아홉이다: `계류` `공포` `대안반영폐기` `수정안반영폐기` `본회의불부의` `철회` `폐기` `부결` `재의부결`.

> ⚠️ **`decision_result` 로 통과를 세지 마라.** 대통령 거부권 뒤 재의에서 부결된 법안도 그 컬럼은 여전히 `'원안가결'`이다(상법 2208496). `outcome`은 그 경우를 `재의부결`로 먼저 판정한다 — 그게 이 컬럼이 존재하는 첫 번째 이유다.
> 그리고 `'가결'`이라는 값은 **존재하지 않는다.** `decision_result IS NULL`은 미처리이지 부결이 아니다.

> ⚠️ 모르는 심사상태는 조용히 `계류`로 떨어진다. 감사의 `review_status_values` 가 원천의 값 집합을 그대로 보여 주므로, 못 보던 값이 나오면 유도 규칙을 손볼 때다.

**`bill_proposers`만 조인하면 가결 법안의 64%가 사라진다.** 위원장 대안(934건)·정부제출(601건)에는 개별 의원 발의자가 없는데, 하필 법이 되는 것은 대부분 그쪽이다. "정당별 통과 법안 수"를 물으면 **반드시 `bills.proposer_kind`로 그 둘을 따로 세라.**

**대표발의가 한 명이라고 가정하지 마라.** 공동대표발의가 있다(`최형두의원ㆍ이준석의원ㆍ황정아의원 등 11인` — 2219709는 대표가 셋이다). `role='대표발의'`가 여러 행일 수 있으므로 `LIMIT 1`이나 `MIN()`으로 접으면 나머지 대표가 사라진다.

**`bill_stages`와 `bill_meetings`는 다른 질문에 답한다.** 섞으면 둘 다 틀린다.

| 묻는 것 | 보는 곳 |
|---|---|
| **어디에 언제부터** 묶여 있나 (회부일·처리일·결과) | `bill_stages` |
| **어떻게 다뤄졌나** (회의명·회의일·회의결과·회의록) | `bill_meetings` |

상정일은 `bill_stages`에 없다 — 소관위·소위 모두 98%가 첫 회의일과 같아서 `bill_meetings`가 답한다. 반대로 **회의가 열리기 전의 상태는 `bill_meetings`에 아예 안 보인다**: 소위는 회부만 되고 회의가 한 번도 안 열린 것이 8,617건, 소관위는 3,889건이다. "언제부터 계류 중인가"는 `bill_stages.date_referred`가 유일한 답이다.

**`bill_stages`는 언제나 LEFT JOIN이다.** 대안·정부제출은 소관위 회부 단계 자체가 없어 행이 아예 없거나 적다. INNER JOIN하면 법이 될 가능성이 가장 높은 법안들이 빠진다.

**단계는 넷뿐이다**: `소관위` `소위` `체계자구` `본회의`. 정부이송일·공포일은 `bills`의 컬럼이고(`date_transferred`·`date_promulgated`), 관련위는 원천이 위원회명과 회부일 말고는 전부 비워 보내서 담지 않는다.

**대안 관계는 `bill_alternatives`로 묻는다.** 양방향이 같은 표에 있다 — `bill_no`가 흡수된 원안, `alt_bill_no`가 흡수한 대안이다.

```sql
-- 이 원안이 어느 대안에 흡수됐나
SELECT alt_bill_no FROM bill_alternatives WHERE bill_no = ?
-- 이 대안이 무엇들을 흡수했나
SELECT bill_no FROM bill_alternatives WHERE alt_bill_no = ?
```

> ⚠️ **`bills.ref_bill_id`로 대안 관계를 묻지 마라.** 그 컬럼은 두 얼굴이다 — 4,156건에서는 흡수한 대안이 맞지만 241건은 다른 관계이고 대상이 임시번호라 우리 목록에 없다.

**공포된 법률의 이름은 `bill_promulgated_laws`에 있고 의안당 여러 행이다.** 일괄개정 의안 하나가 법률 열 개를 공포한다(2201193). 그리고 공포법률명은 **의안명과 다르다** — 의안명 `…기본법안(대안)` → 공포법률명 `…기본법`. 바깥 자료와 이름으로 맞출 때는 이쪽을 쓴다.

**`bill_votes`에 행이 없는 것은 불참이 아니다.** 원천이 찬성·반대·기권 명단만 주고 불참자 명단은 주지 않는다. 불참 수는 `bill_vote_summary`의 재적·재석으로 **계산**하고, 명단으로 유도하지 마라.

**소위원회 이름은 `상위 위원회 + 공백 + 소위명`이다.** `WHERE committee_name = '법안심사제1소위원회'`는 **0건**을 준다 — 저장된 이름이 `'법제사법위원회 법안심사제1소위원회'`이기 때문이다. 소위 이름이 위원회를 넘어 중복되기 때문에(`법안심사제1소위원회`는 법사위·행안위·복지위·정무위에 전부 있다) 이렇게 두지 않으면 한 행이 여러 위원회를 겸한다. 어떤 위원회의 소위를 전부 보려면 `parent_committee`로 걸러라.

**안건과 발언을 잇지 마라.** 회의에 어떤 안건이 상정됐는지는 알지만 개별 발언이 어느 안건에 대한 것인지는 알 수 없다. 의원마다 질의 순서가 다르고 안건을 하나씩 끝내는 방식이 아니다.

**발언에서 의원까지는 두 홉이다.** `meeting_utterances.speaker_no` → `meeting_speakers` → `open_na_id`. 그 사이 `speaker_no`는 사람의 식별자가 아니라 회의 안의 자리번호이고, **회의 밖에서 참조하면 안 된다.** 화자의 42%가 의원이 아니라서(차관·청장·전문위원) 이 단계가 필요하다.

## 데이터 경계 — 무엇이 없는지

**본회의 회의록**(표결 숫자와 의원별 표는 의안 쪽에서 온다), **법안 조문 원문**(HWP/PDF. 제안이유 텍스트만 있다), **22대 이전 대수**, **현행 법령·판례·유권해석**(법제처 소관 — 이 DB의 `bills`는 *발의된 의안*이지 *시행 중인 법*이 아니다), **국회 예정 일정**("다음 주 상임위에 뭐가 올라오나"에 답할 수 없다), **국민동의청원**.

`members.mona_cd`는 비어 있을 수 있다. 국회 명부 API가 봇 차단으로 막혀 있어서다 — 조인에는 쓰이지 않으므로 기능상 잃는 것은 없다.

## 도구

```bash
uv run {skill_dir}/Scripts/db.py schema --db …        # .schema 출력
uv run {skill_dir}/Scripts/db.py selftest --db /tmp/t.db   # ⚠️ 대상 DB를 지운다
uv run {skill_dir}/Scripts/audit.py --db …            # 불변조건만
uv run {skill_dir}/Scripts/verify.py                  # 국회 사이트가 바뀌었나 (DB를 안 본다)
```

**수집이 조용히 빈손으로 오면 파서를 뜯기 전에 `verify.py`를 돌려라.** `selftest`는 우리 코드의 회귀를 잡고(네트워크 없음), `verify.py`는 원천이 바뀌었는지를 실데이터로 본다(DB 없음). 둘은 다른 질문에 답한다.

> ⚠️ **`selftest`는 `--db`가 필수이고 실제 `CONGRESS.db`를 지목하면 거부한다.** 첫 동작이 대상 파일 삭제라서, 기본값이 실제 DB인 채로 인자를 잊으면 수집물이 통째로 사라진다. News 프로젝트에서 실제로 그렇게 4.25GB를 잃었다.
