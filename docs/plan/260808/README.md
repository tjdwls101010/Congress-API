## 한 문단 요약

대한민국 국회의 **법률안 · 국회의원 · 회의록**을 국회 웹사이트에서 긁어 로컬 SQLite에 적재하고, 클로드가 그 위에서 SQL로 자유롭게 탐색하는 스킬을 만든다. 국회 OpenAPI는 쓰지 않는다 — 상당수가 작동하지 않고 웹사이트와 값이 어긋나기 때문이다. 목적은 조회 자동화가 아니라 **클로드가 국회를 실제로 아는 상태를 만드는 것**이고, DB는 그 판단의 재료다.

## 확정된 결정

계획 세션에서 사용자와 합의한 것들이다. 구현 중에 뒤집고 싶어지면 **먼저 물어라** — 여기 적힌 것은 전부 대안을 놓고 고른 결과다.

| 항목 | 결정 | 비고 |
|---|---|---|
| 대수 범위 | **22대만** (2024-05-30~) | 스키마에 `assembly_unit`을 두어 나중에 넓힐 수 있게 |
| 의안 종류 | **목록은 전체 의안, 상세는 법률안만** | 의안번호 연속성 검증이 성립하려면 목록이 전체여야 한다 |
| 법안 내용 | **제안이유 및 주요내용 텍스트만** | 조문 원문(HWP/PDF)은 받지 않는다 |
| 의안 PK | **의안번호**(`bill_no`) | 시스템 코드는 `bill_id`로 UNIQUE 보관. **접두어가 `PRC_`와 `ARC_` 둘이다**(정부제출 470건) |
| 의원 PK | **`open_na_id`** (slug, 예: `KIMHyun`) | `mona_cd`는 UNIQUE·**nullable**. 명부 API가 막혀 못 채울 수 있다 |
| 발의자 | **대표발의 + 공동발의 모두** | |
| 정당 이력 | **현재 정당만. 이력 테이블 없음** | 수집 이전 변경은 어차피 못 채워서 값을 못 낸다 |
| 회의록 범위 | 상임위 · 예결위 · 특위 · 국정감사 · 국정조사, **소위원회 포함** | **본회의 회의록은 제외** |
| 회의록 저장 | **회의 / 화자 / 발언 3층 정규화** | 지역구·정당은 `members`에서 조인 |
| 본문 검색 | **LIKE만** | FTS5 trigram은 2자 질의에 조용히 0건을 준다 |
| 수집 실행 | **Python 스크립트 직접 HTTP** | `claude-in-chrome`은 정찰 전용 |
| 자동화 | **GitHub Actions cron + self-hosted 러너**, 하루 1회 새벽 | News 스킬과 동일 구조 |
| DB 위치 | `.claude/skills/congress/CONGRESS.db` | git에는 커밋하지 않는다 |
| 수집 속도 | **실측해서 정한다** | 06번 문서의 측정 절차를 따른다 |

## 이 계획이 기대는 두 가지 선행 자산

**News 스킬** (`.tmp/Naver-News/.claude/skills/News`) — 같은 사용자가 만든, 같은 모양의 스킬이다. 완결성 원장, "corpus에는 완성 행만", 불변조건 기반 성공 판정, 스키마 주석에 함정을 적는 방식이 전부 거기서 왔다. **구현 전에 그 SKILL.md와 `Scripts/newsdb.py`를 읽어라.** 이 계획은 그 문서들의 판단을 국회 도메인에 옮긴 것이고, 옮기면서 달라진 부분만 근거를 적어 두었다.

**이전 Congress-DB** (`github.com/tjdwls101010/Congress-DB`) — 같은 사용자가 OpenAPI로 만들었다가 **버리기로 한** 프로젝트다. 스키마와 코드는 가져오지 않는다. 다만 거기 기록된 것 중 *국회 데이터 자체의 성질*인 함정은 출처와 무관하게 유효해서 03번 문서에 옮겨 적었다.
