# 데이터 원천 — 실측 정찰 결과

이 문서의 내용은 **2026-08-08에 `claude-in-chrome`으로 실제 호출해 확인한 것**이다. "아마 이럴 것"은 적지 않았고, 확인하지 못한 것은 [07-미해결-확인사항.md](07-미해결-확인사항.md)로 뺐다.

전부 평범한 HTTP POST/GET이다. **수집은 Python `httpx`로 직접 친다** — 브라우저 자동화는 정찰용이었고, 의안 2만 건 규모에서는 며칠이 걸리고 탭 하나가 죽으면 무너진다.

## ⚠️ 브라우저 밖에서 되는지 실제로 확인했다

브라우저 콘솔에서 되는 것이 `httpx`에서도 된다는 보장은 없다. 그래서 **`curl`로 따로 시험했다**(브라우저와 완전히 분리된 클라이언트).

| 대상 | curl 결과 |
|---|---|
| likms 의안 상세 GET | ✅ 200. `announceDt`까지 그대로 |
| likms 의안 목록 POST | ✅ 200 (단, 63필드를 다 보내야 행이 온다) |
| record 회의록 본문 GET | ✅ 200. `spk_sub` 694개 · `/members/` 74개 |
| record 회의 목록 POST | ✅ 200 — **단, 세션 쿠키가 필요하다**(아래) |
| www 의원 상세 GET | ✅ 200. 선거구·정당 그대로 |
| **www 명부 JSON API** | ❌ **403** — 헤더를 갖춰도 막힌다 |

**① POST 엔드포인트는 세션 쿠키가 필요하다.** 쿠키 없이 `record`의 `cmit.do`를 치면 **200에 본문은 오는데 회의 id가 하나도 없다** — 에러가 아니라 빈 결과라 알아채기 어렵다. 해당 페이지를 GET해서 쿠키를 받아 두면 정상적으로 4건이 온다. `httpx.Client`처럼 **쿠키를 유지하는 세션 객체를 쓰고, 각 호스트마다 진입 페이지를 한 번 GET하고 시작하라.**

**② 의원 명부 JSON API는 브라우저 밖에서 403이다.** User-Agent · 세션 쿠키 · Referer · Origin · Accept를 다 갖춰도 403에 본문 0바이트다. 브라우저에서는 정상 동작한다. 봇 차단으로 보이며, **우회를 시도하지 않았다.**

이건 계획의 위험 요소이므로 대안을 적어 둔다 — 구현 시 순서대로 시도하라.

1. **`httpx`로 그냥 해 본다.** curl과 TLS 스택이 달라 결과가 다를 수 있다. 공짜 시도다
2. **의원 상세 페이지로 대체한다.** `www.assembly.go.kr/members/22nd/{slug}`는 curl로 잘 되므로, slug 목록만 다른 데서 얻으면 프로필은 전부 받을 수 있다. 표결·발의자·발언에 slug가 나오므로 목록은 거기서 모인다
3. **명부만 브라우저로 받는다.** 299명이고 한 달에 한 번이면 충분하다. 나머지 수집 전체는 `httpx`로 두고 이 한 조각만 예외로 두는 것이 합리적이다

**`monaCd`는 이 JSON API에만 있다.** 2·3번으로 가면 `mona_cd`를 못 채울 수 있으니, 스키마에서 `NOT NULL UNIQUE`를 유지할지 재판단해야 한다.

## 1. 의안 목록

```
POST https://likms.assembly.go.kr/bill/bi/bill/sch/findSchPaging.do
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
X-Requested-With: XMLHttpRequest
```

**응답은 JSON이 아니라 HTML 조각**이다. `<tr>` 행 목록 + 페이지네이터 + 인라인 `<script>`가 함께 온다.

### 파라미터

폼(`document.forms['form']`)에 필드가 **63개** 있고, 그중 일부만 채워도 나머지는 빈 문자열로 보내야 한다. **빈 값을 생략하면 목록 행이 안 오고 페이지네이터만 온다** — 정찰 중 실제로 겪은 함정이다. 총건수는 정상적으로 오기 때문에 "필터는 먹었는데 행이 없다"로 보여 원인을 찾기 어렵다.

의미 있는 것만:

| 파라미터 | 값 | 뜻 |
|---|---|---|
| `ageFrom` / `ageTo` | `22` / `22` | 제안 대수 범위 |
| `fromPropDt` / `toPropDt` | `2026-08-06` | 제안일자 범위 (`YYYY-MM-DD`) |
| `page` | `1` | 1부터 |
| `rows` | `1000` | **1000 확인됨** |
| `billKind` | (비움) | 의안종류. **비워 둔다 — 전체 의안을 받아야 한다** |
| `_csrf` | 페이지의 `input[name=_csrf]` | |

그 밖에 `fromSubmitDt`/`toSubmitDt`(접수일), `fromGovTransDt`/`toGovTransDt`(정부이송일), `procGbnCd`(처리구분), `cmtResultCd`(위원회 처리결과), `srchCmtId`(소관위) 등의 범위·필터가 있다. 갱신 전략에서 쓸 수 있다.

### 응답에서 뽑는 것

행마다 `data-` 속성으로 키가 직접 박혀 있다. 텍스트 파싱이 필요 없다.

```html
<tr>
  <td>2220510</td>
  <td><a data-bill_no="2220510"
         data-bill-id="PRC_A2I6J0H8H0F7E1F4M1N1M2M5K4J5K6"
         onclick="goDetailPage(this);">…</a></td>
  …
</tr>
```

컬럼 순서: `의안번호 · 의안명 · 제안자구분 · 제안일자 · 의결일자 · 의결결과 · 제안이유(아이콘) · 심사진행상태`

의안명 셀에는 `계류의안` / `처리의안` 같은 상태 배지 텍스트가 앞에 붙는다. **의안명만 떼어낼 때 이걸 같이 가져오지 않도록 주의하라** — 배지는 별도 자식 요소다.

### 실측 수치

- 22대 전체 의안: **20,598건** (2026-08-08 기준)
- `rows=1000` 요청 1회: 응답 **1.6MB**, **1.9초**
- `rows=100`은 1.27초 — 요청당 고정비가 크므로 **1000을 쓰는 게 압도적으로 유리하다**
- 22대 전체를 훑는 데 **21회 요청**이면 된다

### 의안번호는 빈틈없이 연속이다 — 전수로 확인했다

**22대 20,598행을 전부 받아 검사했다**(21페이지 × rows=1000). 표본이 아니다.

```
총 20,598행
├ 숫자 의안번호 20,510건 → 2200001 ~ 2220510
│                          구간 크기 20,510 · 구멍 0 · 중복 0   ← 완벽한 연속
└ ZZ 형식        88건   → ZZ22121 · ZZ22124 …
```

의안번호는 `22` + 5자리 일련번호다. **그래서 완결성을 산술로 증명할 수 있다** — "2200001부터 최대까지 전부 있는가"를 SQL 한 줄로 묻는다. News 스킬의 셀 원장보다 강한 보증이다.

> ⚠️ **`ZZ` 형식 88건이 있다.** 국정조사계획서·기금운용평가보고서처럼 의안번호 체계 밖의 문서다. `bill_no`를 정수로 두면 이 88건이 깨지므로 **TEXT로 저장하고, 완결성 검증은 숫자인 것만 대상으로 한다.**

**두 billId 접두어를 다 받아야 한다.** 전수 집계 결과 `PRC_` 20,128건 · **`ARC_` 470건**이다. `ARC_`는 정부제출 쪽에서 나온다 — `PRC_`만 가정하고 정규식을 짜면 조용히 누락된다.

연속성은 **목록을 전체 의안으로 받을 때만 성립한다.** 법률안만 받으면 예산안·결의안 자리에 구멍이 생기고, 그 구멍이 비법률안인지 수집 실패인지 구분할 수 없게 된다. `billKind`를 채우고 싶어지면 이 문단을 다시 읽어라.

### 제안자구분으로 거를 수 있다

`proposerKind` 옵션: `의원` · `위원장` · `정부` · `의장` · `대통령` · `기타`. 22대 실측 — **위원장 934건 · 정부 601건.**

`reexamYn=Y`로 **재의(대통령 거부권) 대상 28건**을 바로 뽑을 수 있다. `procGbnCd`는 `G`(계류) / `P`(처리)다.

> `lawStatus`는 공포 여부가 아니라 **제정 / 전부개정 / 일부개정 / 헌법개정 / 폐지**를 가르는 필터다. 이름에 속지 마라.

## 2. 의안 상세

```
GET https://likms.assembly.go.kr/bill/bi/billDetailPage.do?billId={PRC_…}
```

> ⚠️ **서버 렌더링이 아니다.** 초안은 그렇게 적었는데 틀렸다 — 브라우저가 렌더링한 DOM을 보고 오해한 것이다. 원시 응답을 문자열로 검사하면 `의안접수정보`·`제안자` 같은 캡션이 **아예 없다.** 심사 단계 테이블은 아래 `billInfo.do`가 따로 가져온다.

이 GET에서 얻는 것은 둘이다.

**① 숨은 input의 구조화 메타데이터.** 텍스트를 파싱하기 전에 `input[type=hidden]`을 먼저 봐라. 훨씬 안정적이다.

| 필드 | 예시 | 뜻 |
|---|---|---|
| `billNo` | `2215928` | 의안번호 |
| `billKindCd` | `법률안` | **의안종류. 이름에서 추정할 필요가 없다** |
| `selRefBillId` | `PRC_Z2Z6…` | **대안반영폐기 시 흡수한 대안 법률안** |
| `reexamYn` | `N` | **재의(대통령 거부권 후) 대상 여부** |
| `billGbnCd` | `대안` 또는 빈값 | **대안인가 원안인가.** 위원장 대안에서 `대안`으로 온다 |
| `currCmtName` | `위원회 심사` | 현재 심사 단계 |
| `withdrawCnt` | `0` | 철회 건수 |
| `tmprAnYn` | `N` | 의미 미확인 — [07번](07-미해결-확인사항.md) 참조 |
| `headMemoInfo` | `비용추계요구서 제출됨.` | 상단 메모 |

**② 값으로 박혀 있는 접수정보.** 캡션은 없어도 데이터는 있다 — 제안일자(`2025-11-27`) · 제안자 요약(`이해민의원 등 13인`) · 소관위원회 · 의결결과가 원시 응답에 문자열로 존재한다. 제안회기만 조립된 형태라 원시 응답에서 바로 안 잡힌다.

**③ 대표발의의원 카드.** 이게 대표발의자를 가르는 **유일하게 확실한 근거**다.

```html
<a href="https://www.assembly.go.kr/members/22nd/LEEHAIMIN">대표발의의원 이해민의원</a>
```

발의자 팝업(4번)은 대표발의를 **전혀 표시하지 않는다** — 클래스도 라벨도 없고 대표발의자가 그냥 목록 맨 앞에 있을 뿐이다. 순서에 기대지 말고 이 카드를 써라. 위원장 대안과 정부제출에는 이 카드가 아예 없다.

### 심사 단계는 별도 요청이다

```
POST https://likms.assembly.go.kr/bill/bi/bill/detail/billInfo.do
```

> ⚠️ **`billId`만 보내면 테이블이 일부만 온다.** 이게 이 엔드포인트의 가장 큰 함정이다.
> `billId`만으로 호출하면 200에 그럴듯한 응답이 오는데 **의안접수정보·정보이송정보·공포정보가 빠져 있다.**
> 에러가 아니라 조용한 결손이라, 공포된 법률을 받고도 "공포 테이블이 없네"라고 오판하게 된다.
> 계획 세션에서 실제로 그렇게 오판해 "22대에 공포된 법률 예제를 못 찾겠다"고 적을 뻔했다.
>
> **해결: `<form id="form" name="form">` 안의 필드만 되돌려 보낸다.** 페이지가 그렇게 한다.
>
> ⚠️ **"숨은 input 전부"로 이해하면 안 된다.** 페이지의 hidden input 81개는 서로 다른 세 form
> (`form`·`historyForm`·`global-hidden-form`)에 흩어져 있고 `billNo`·`reexamYn`이 **두 form에 중복**된다
> — `form`에는 실제 값이, `historyForm`에는 검색조건 echo용 **빈 문자열**이 들어 있다.
> 81개를 이름→값 딕셔너리로 접으면 뒤에 오는 빈 값이 이겨 `billNo=''`가 되고,
> **200에 캡션 7개가 다 오는 것처럼 보이는데 공포번호·공포법률명 칸만 빈다.**
>
> 보낼 12개: `billId` · `billNo` · `billKindCd` · `currCmtName` · `reexamYn` · `billGbnCd` ·
> `tmprAnYn` · `govTransDt` · `announceDt` · `withdrawCnt` · `intrsBillCnt` · `stageMemo`

`govTransDt`(정부이송일)·`announceDt`(공포일)를 서버가 되받아 그 테이블을 렌더링하는 구조다. 그래서 **그 두 값은 이미 GET의 숨은 input에 있다** — 날짜만 필요하면 두 번째 요청 없이도 얻는다. 공포번호와 공포법률명만 이 응답에 있다.

실측 응답 크기: 의원발의 25.7KB(테이블 6개) · 위원장안 11.0KB(2개) · 정부제출 6.6KB(1개) · 공포된 법률 28.8KB(7개).

`selRefBillId`가 특히 중요하다. 이전 프로젝트는 OpenAPI에 대안 관계 필드가 없어 이 값을 따로 스크래핑해야 했다(22대 대안반영폐기 3,676건 + 수정안반영폐기 39건). 우리는 처음부터 이 페이지를 긁으므로 공짜로 따라온다.

### 심사 단계 테이블

`<table>`에 `<caption>`이 붙어 있어 **caption 텍스트로 어느 테이블인지 판별한다.** 클래스나 순서에 의존하지 마라 — 의안마다 존재하는 테이블이 다르다.

| caption 시작 | 컬럼 |
|---|---|
| `의안접수정보` | 의안번호 · 제안일자 · 제안자 · 제안회기 · 문서 |
| `소관위 심사정보` | 소관위원회 · 회부일 · 상정일 · 처리일 · 처리결과 · 문서 |
| `소관위 회의정보` | 회의명 · 회의일 · 회의결과 · **회의록** |
| `소위 심사정보` | 소위원회 · 회부일 · 상정일 · 처리일 · 처리결과 |
| `관련위 심사정보` | 관련위원회 · 회부일 · 상정일 · 의견서제시일 · 문서 |
| `법사위 체계자구 심사정보` | 회부일 · 상정일 · 처리일 · 처리결과 · 체계자구검토보고서 |
| `법사위 회의정보` | 회의명 · 회의일 · 회의결과 · 회의록 |
| `본회의 심의정보` | 상정일 · 의결일 · 회의명 · 회의결과 · 회의록 |
| `정보이송정보` | 정부이송일 · 문서 |
| `공포정보` | 공포일자 · 공포번호 · 공포법률 |

> `정보이송정보`는 오타가 아니다 — 국회 쪽 caption이 실제로 그렇게 적혀 있다(화면 제목은 "정부이송정보"). **caption으로 매칭한다면 이 오타를 그대로 써야 한다.**

공포까지 간 법률의 실측 예(AI 기본법, 의안번호 2206772):

```
정보이송정보 : 정부이송일 2025-01-10
공포정보     : 공포일자 2025-01-21 · 공포번호 20676
               공포법률 인공지능 발전과 신뢰 기반 조성 등에 관한 기본법
```

**공포법률명은 의안명과 다르다.** 의안명은 `인공지능 발전과 신뢰 기반 조성 등에 관한 기본법안(대안)`이고 공포법률명은 `…기본법`이다 — `안(대안)` 꼬리가 떨어진다. 법제처 등 바깥 자료와 이름으로 맞출 때 쓰는 것은 공포법률명 쪽이다.

`관련위 심사정보`는 예제 하나에만 있었다. 테이블 목록을 고정으로 가정하지 말고 **caption을 보고 있는 것만 처리하라.**

### 캡션 테이블 밖에 있는 것 — `bill_memo`

```html
<pre class="bill_memo">
※ 2025. 4. 1. 헌법 제53조에 따라 대통령으로부터 재의요구서가 제출됨.
※ 2025. 4. 17. 본회의에 재의를 부친 결과 부결됨.
</pre>
```

**재의결 결과가 오직 여기에만 있다.** 위 예(상법 2208496)는 재의에서 **부결**됐는데 목록의 의결결과는 여전히 `원안가결`이고, `voteInfo.do`에도 원표결 한 세트만 온다.

caption 매칭 파서는 이걸 절대 못 잡는다 — 테이블이 아니기 때문이다. **`<pre class="bill_memo">`를 따로 집어 `bills.status_memo`에 원문 그대로 넣어라.** 문구가 정형이 아니고 종류도 열려 있어 구조화하지 않는다.

### 회의록으로 이어지는 링크 (중요)

`소관위 회의정보` · `법사위 회의정보` · `본회의 심의정보`의 회의록 칸에 이런 링크가 있다:

```
https://record.assembly.go.kr/assembly/viewer/minutes/download/pdf.do?id=56297
```

**이 `id=56297`이 회의록 본문 URL(`xml.do?id=`)의 그 id와 같은 값이다.** 즉 의안 ↔ 회의록 조인이 의안 쪽에서 직접 나온다. 회의록 트리를 훑지 않고도 "이 법안이 논의된 회의"를 알 수 있다.

### 페이지 제목에서

`<title>`이 `[2214631] 소프트웨어 진흥법 일부개정법률안(이해민의원 등 13인) | 심사정보` 형식이라 의안번호·의안명·제안자 요약을 한 번에 얻을 수 있다.

## 3. 표결 정보

```
POST https://likms.assembly.go.kr/bill/bi/bill/detail/voteInfo.do
body: billId={PRC_…}&_csrf=…
```

**상세 페이지의 HTML에는 표결 정보가 없다.** 탭을 눌러야 이 XHR이 나간다 — 원문 HTML에 `재석`·`찬성`이 문자열로 존재하지 않는 것을 확인했다. 상세만 받고 표결이 없다고 판단하면 안 된다.

응답은 HTML. 뽑을 것:

- **요약**: 제안/표결일자, 발의자/제안자, `재석 196인 / 재적 299인`, `수정가결 196인 (찬성 193인, 반대 1인, 기권 2인)`
- **명단**: 찬성/반대/기권 각 탭에 `<ul><li>` 목록. 각 `<li>`가 의원 상세 링크를 갖는다:

```html
<li class="visible">
  <a href="https://www.assembly.go.kr/members/22nd/KANGKYUNGSOOK">
    <span class="pic"><img …></span>
    <span class="txt">…</span>
  </a>
</li>
```

**의원 코드(`monaCd`)는 없고 slug(`openNaId`)만 있다.** 그래서 `members`의 PK를 slug로 잡았다. 이름 문자열로 조인하면 동명이인에서 조용히 틀린다.

### 표결에 관한 함정

**불참은 기록되지 않는다.** 재적 299 / 재석 196이면 103명이 불참인데, 명단 탭은 찬성·반대·기권 셋뿐이다. `bill_votes`에 행이 없는 것은 "불참"이 아니라 **"이 표결에서 그 의원의 표를 우리가 모른다"**이다. 불참자를 세고 싶으면 재적·재석 숫자로 계산하고, 명단으로 유도하지 마라.

**대통령 거부권 후 재의결은 표결이 두 번이다.** 이전 프로젝트는 원표결만 얻었다. 우리 원천에서 두 번이 다 오는지는 미확인 — [07번](07-미해결-확인사항.md) 참조. `reexamYn` 필드가 단서다.

```
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
```

### 파라미터 (전부 보내야 한다)

```
menuNo=600137  cntsDivCd=NAAS  unitCd=100022  pageIndex=1

hgNm=  polyCd=  cmitCd=  upOrigCd=  origCd=  sexGbn=  ageGbn=
```

```json
{

  "resultList": [{
    "rnum": "31",
    "monaCd": "86R9476S",
    "openNaId": "KIMMOONSOO",

```

**`monaCd`가 국회 공식 의원 코드이고 `openNaId`가 우리가 다른 데서 만나는 그 slug다.** 둘을 잇는 유일한 지점이 이 엔드포인트다 — 표결·발언·발의자 어디에도 `monaCd`가 없기 때문이다.

## 6. 의원 상세 — 전직 의원까지 여기서 해결된다

```
GET https://www.assembly.go.kr/members/{대수}/{slug}
예: https://www.assembly.go.kr/members/22nd/KIMHyun
```

대수는 `22nd`처럼 **영문 서수**이고 이름 자리는 **한글이 아니라 slug**다.

**slug의 대소문자는 규칙이 없다** — `KIMHyun` · `CHOIMinhee` · `KANGKYUNGSOOK` · `LEEHAIMIN` · `CHUNJAESOO`가 전부 다른 패턴이다. 이름에서 만들어낼 수 없다. **반드시 원천의 href나 명부의 `openNaId`에서 가져와라.**

`curl`로도 200이다 — 브라우저가 필요 없다.

### 임기 중 떠난 의원도 페이지가 살아 있다

**실측 확인.** 전재수 의원은 22대 중 사직했는데 `/members/22nd/CHUNJAESOO`가 여전히 **HTTP 200 · 74KB**로 응답하고 이름·정당·선거구가 그대로 있다.

**이게 설계에 주는 함의가 크다.** 표결·발의자·발언에서 만난 slug는 그 사람이 지금 의원이든 아니든 **상세 페이지로 프로필을 채울 수 있다.** 전직 의원 명부를 따로 파싱할 필요가 없고, 403이 걸린 명부 JSON API에 대한 의존도 크게 줄어든다.

### 전직 의원은 페이지가 스스로를 표시한다

현직 여부를 판정하려고 명부와 대조할 필요가 없다. **HTML이 직접 말해 준다.**

```html
<div class="info_name jeonzik_name">   ← 전직(前職). 현직 페이지에는 이 클래스가 없다
```

실측 — 전재수 페이지에 `jeonzik` 4회 등장, 김현(현직) 페이지에 **0회**. `is_incumbent`는 이 클래스 유무로 정한다.

전직 페이지에는 **사직 의안으로 가는 링크**까지 있다(`title="국회의원(전재수) 사직의 건"` + `billId`). 그 의안은 우리 `bills`에도 들어와 있으므로 "언제 왜 떠났는가"를 의안 쪽에서 확인할 수 있다.

### 현직과 전직은 필드 구성이 다르다

| | 현직 (김현) | 전직 (전재수) |
|---|---|---|
| 이름 · 한자명 · 정당 | ✅ | ✅ |
| 선거구 | ✅ `경기 안산시을` | ✅ (요약 줄에 포함) |
| 당선횟수 | ✅ `재선(제19대, 제22대)` | ✅ `3선(제20대, 제21대, 제22대)` |
| 소속위원회 | ✅ | ❌ **없다** |
| 사무실 전화·호실·이메일·보좌진 | ✅ | ❌ 없다 |
| 구조 | `<dl><dt>/<dd>` 항목 12개 | 요약 한 줄 |

**전직 의원은 `member_committees`가 비는 것이 정상이다.** 파서는 두 레이아웃을 모두 다뤄야 하고, 전직 쪽에서 `<dl>` 항목을 못 찾았다고 실패로 처리하면 안 된다.

현직 페이지의 `<dl>` 항목: 의원홈페이지 · 선거구 · 소속위원회(쉼표 구분) · 당선횟수 · 사무실 전화 · 사무실 호실 · 개별 홈페이지 · 이메일 · 보좌관 · 선임비서관 · 비서관 · 의원실 안내.

## 7. 회의록 목록 — 필요한 건 id 열거뿐이다

**트리 구조를 모델링할 이유가 없다.** 회의의 메타(대수·회기·차수·위원회·일자)는 회의록 **본문 첫머리에 한 줄로 다 있다**(8절). 그래서 목록 쪽이 할 일은 하나뿐이다 — **conference id를 빠짐없이 열거하는 것.**

이 구분이 중요하다. 트리에서 위원회·회기·차수를 파싱해 `meetings`를 채우려 들면 트리 구조에 결합되고, 그쪽이 바뀌면 깨진다. id만 받아 오면 트리가 어떻게 생겼든 상관없다.

### 열거 프로토콜 — 다섯 종류 전부 실측 검증됨

**한 번의 요청으로 한 위원회의 전 회기 회의가 다 온다.** 회기를 돌 필요가 없다.

**① 위원회 코드를 얻는다.** 트리 페이지의 아코디언 헤더가 `data-` 속성으로 들고 있다.

```
GET https://record.assembly.go.kr/assembly/mnts/total/22.do?class_id_sch={2|3|4|5|6}&cmit_chk=all
→ <a class="tit cmit" id="cmit_AA" data-th="22" data-class="2" data-cmit="AA" data-chk1="all">국회운영위원회</a>
```

`a.tit.cmit[id^=cmit_]`를 훑어 `data-cmit`을 모은다. **코드를 하드코딩하지 마라** — 페이지가 준다.

**② 위원회별로 회의 id를 받는다. `sess_sch`를 비운다.**

```
POST /assembly/mnts/async/cmit.do
th_sch=22 & class_id_sch=2 & sess_sch= & cmit_cd_sch=AA & cmit_chk=all
& cmit_chk_cmit= & cmit_chk_sub= & cmit_chk_etc=
```

응답에 `xml.do?id=57025` · `pdf.do?id=57025` · `data-mnts_id="57019"`가 들어 있다. **이 id가 회의록 본문 URL의 그 id다.**

> **`sess_sch`를 비우는 것이 핵심이다.** 채우면 그 회기만 오고(제437회 → 4건), 비우면 **그 위원회의 22대 전체**가 온다(국회운영위 → **45건**, 4건은 그 부분집합). 회기 목록을 따로 받아 회기마다 도는 것은 요청을 14배로 늘릴 뿐이다.
>
> 그래서 `sessCmit.do`(회기 목록)는 **열거에 필요 없다.** 회기 구분은 회의록 본문의 메타에서 나온다.

> ⚠️ **`cmit_chk=all`이면 소위원회 회의가 상위 위원회 응답에 함께 온다.** 소위를 따로 훑지 마라.

### 예결위(class=4)만 트리 모양이 다르다

**다섯 종류의 트리 최상위를 전부 실측했다.** 하나로 일반화했다가 한 종류가 통째로 빌 뻔했다.

| class | 종류 | 최상위 | `data-cmit` | 경로 |
|---|---|---|---|---|
| 2 | 상임위원회 | 위원회 | **20개** | ①② 그대로 |
| 3 | 특별위원회 | 위원회 | **14개** | ①② 그대로 |
| 5 | 국정감사 | 위원회 | **18개** | ①② 그대로 |
| 6 | 국정조사 | 위원회 | **5개** | ①② 그대로 |
| **4** | **예산결산특별위원회** | **회기** | **0개** | **①이 성립하지 않는다** |

**예결위는 위원회가 하나뿐이라 트리 최상위가 곧 회기 목록이다**(`data-sess` 8개). `data-cmit`이 0개라서 ①의 위원회 루프가 **에러 없이 0회 돌고 끝난다** — 담겠다고 한 회의 종류가 조용히 전부 빈다.

예결위는 `data-sess`를 모아 회기마다 ②를 부른다. `cmit_cd_sch`는 빈 값이든 `G1`이든 결과가 같다.

### 실측 기준값 — 구현 검증에 그대로 쓴다

각 class의 **첫 위원회(AA)** 기준이다. 이 숫자가 안 나오면 경로가 틀린 것이다.

```
class=2 상임위   AA(국회운영위) → 45건    (sess=437 단독은 4건: 57010·57019·57025·57051)
class=3 특위     AA             →  6건
```

## 8. 회의록 본문 — 가장 깨끗한 원천

```
GET https://record.assembly.go.kr/assembly/viewer/minutes/xml.do?id={회의록id}&type=view
```

이름이 `xml.do`지만 **응답은 HTML**이다. 그리고 시맨틱 클래스가 붙어 있어 파싱이 안정적이다.

### PDF가 아니라 이 HTML을 쓰는 이유

PDF에서는 화자와 발언을 레이아웃 휴리스틱으로 추측해야 하지만, 여기서는 **필드가 이미 나뉘어 있다.**

```html
<div class="in_chk">…</div>
<div class="man">
  <a href="https://www.assembly.go.kr/members/22nd/KIMHyun">
    <span class="pic"><img …></span>
    <span class="txt">
      <span class="position">소위원장</span>
      <strong class="name">김현</strong>
      <span class="area">(경기 안산시을)</span>
    </span>
  </a>
</div>
<div class="talk">
  <div class="txt">
    <span class="spk_sub">정보통신방송법안심사소위원회 김현 위원장입니다.</span><br>
    <span class="spk_sub">우리 소위원회는 2월 24일 …</span><br>
    …
  </div>
</div>
```

- `.speaker` — 발언 블록
- `.man` — 화자 (`.position` 직위, `.name` 이름, `.area` 선거구)
- `.man a[href*="/members/"]` — **있으면 국회의원, 없으면 비의원**
- `.talk .spk_sub` — 발언 문단. 여러 개가 `<br>`로 이어진다

### 질의자/답변자 판별은 실측으로 확인됐다

회의록 56297(제22대 제432회 제3차 과학기술정보방송통신위원회, 2026-02-25):

```
발언 블록 105개
  ├ /members/ 링크 있음  61개  → 국회의원
  └ 링크 없음            44개  → 비의원
```

링크 없는 쪽의 `.position` 실제 값: `과학기술정보통신부제2차관` · `방송미디어통신위원장` · `과학기술정보통신부제1차관` · `우주항공청장` · `수석전문위원` · `전문위원`

링크 있는 쪽: `위원장` · `소위원장` · `소위원장대리` · `위원`

**직위 문자열로 분류하려 들지 마라.** 링크의 유무가 판별자다 — 직위는 종류가 열려 있고 회의마다 새로 생긴다.

### 화자는 발언보다 훨씬 적다

발언 블록 105개에 **고유 화자는 20명 안팎**이다. 그래서 `meeting_speakers`를 따로 두고 발언이 그것을 참조한다. 발언마다 직위·선거구를 반복하면 같은 사실이 수백 번 중복된다.

### 회의 메타데이터

본문 첫머리에 한 줄로 온다:

```
제22대국회 제432회 (임시회) 제3차 과학기술정보방송통신위원회(2026.02.25.)
```

대수 · 회기 · 회기종류 · 차수 · 위원회 · 일자가 전부 여기서 나온다.

페이지의 다른 섹션: `상정된 안건` · `안건정보` · `부록` · `영상회의록` · `발언자` · `회의정보`

### 상정 안건은 의안과 직접 연결된다

```html
<p class="tit_sm angun pl10">
  <a href="https://likms.assembly.go.kr/bill/billDetail.do?billId=PRC_O2M5V0V1T0U9S1T8R0S2Z3Y5Z1X3X8">
    100. 방송법 일부개정법률안(김현 의원 대표발의)(의안번호 2207480)
  </a>
</p>
```

`.angun` 요소가 **billId와 의안번호를 둘 다** 준다. 이 회의는 안건이 122개였다.

> ⚠️ **안건은 회의 단위이지 발언 단위가 아니다.** 회의가 어떤 안건을 상정했는지는 알 수 있지만, **개별 발언이 어느 안건에 대한 것인지는 알 수 없다.** 의원마다 질의에서 다루는 순서가 다르고, 안건을 하나씩 끝내고 넘어가는 방식이 아니기 때문이다. `meeting_utterances`에 `bill_no`를 두지 마라 — 그 컬럼은 채우는 순간 거짓이 된다.

여기의 의안 상세 URL이 `/bill/billDetail.do?billId=`로, 의안정보시스템의 `/bill/bi/billDetailPage.do?billId=`와 **경로가 다르다.** billId 값은 같다.
