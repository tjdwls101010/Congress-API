# 스킬 구성

## 하네스 레이어 배치

각 요소를 어느 층에 둘지의 판단이다. 잘못 두면 매 세션 토큰을 내거나(CLAUDE.md에 과적재), 필요할 때 안 뜬다(스킬 설명이 약함).

| 요소 | 층 | 근거 |
|---|---|---|
| 국회 데이터 수집·조회 절차 전체 | **스킬** (`.claude/skills/congress/SKILL.md`) | 국회를 다루는 작업일 때만 필요하다. 매 세션 로드할 이유가 없다 |
| 스키마와 그 함정 | **DB 자체의 주석** | `.schema`가 곧 문서다. 별도 문서를 만들면 이중 장부가 되고 낡는 쪽은 언제나 문서다 |
| 수집 로직 | **번들 스크립트** (`Scripts/*.py`) | |
| 안전장치(실제 DB 삭제 방지 등) | **스크립트의 인자 설계** | 문서는 안 읽히지만 인자는 안 주면 실행이 안 된다 |
| 정기 수집 | **GitHub Actions cron + self-hosted 러너** | News와 동일 구조. 클로드가 붙어 있지 않아도 돈다 |
| "이 저장소에 congress 스킬이 있다" | **CLAUDE.md 두세 줄** | 스킬 존재를 모르면 WebSearch로 새어 나간다 |
| DB 파일 제외 | **`.gitignore`** | |

훅은 만들지 않는다. 이 프로젝트에는 "반드시 매번 일어나야 하는 것"이 없다 — 수집은 cron이 보장하고, 나머지는 판단의 영역이다.

## 파일 배치

```
.claude/skills/congress/
├── SKILL.md
├── CONGRESS.db                 (gitignore)
└── Scripts/
    ├── collect.py              CLI · 오케스트레이션만          ~200줄
    ├── db.py                   스키마 · 연결 · 실패원장         ~600줄 (대부분 DDL 주석)
    ├── http.py                 세션 · 레이트리밋 · 재시도 · CSRF ~150줄
    ├── audit.py                불변조건 · 감사 질의             ~200줄
    ├── bills.py                의안 — 수집과 파싱을 한 파일에    ~500줄
    ├── members.py              의원 — 수집과 파싱               ~250줄
    ├── meetings.py             회의록 — 수집과 파싱             ~400줄
    └── verify.py               원천이 바뀌었는지 실데이터로 확인 ~150줄
```

### 왜 층이 아니라 도메인으로 자르나

`parsers.py`에 파싱을 모으고 `collect.py`에 수집을 모으는 구성이 자연스러워 보이지만, 그러면 **국회가 의안 상세 DOM을 바꿀 때 두 파일을 고쳐야 한다.** 함께 바뀌는 것이 갈라져 있는 것이다.

세 도메인(의안·의원·회의록)은 서로 거의 독립이고 **원천이 바뀌는 단위도 도메인 단위**다. 도메인으로 자르면 한 변경이 한 파일에 갇힌다. 그 대신 도메인을 가로지르는 공통 관심사(HTTP·DB·감사)만 따로 뺀다.

한 파일에 다 넣으면 어떻게 되는지는 참고할 실례가 있다 — News의 `scrape_naver_news.py`는 1,323줄, `newsdb.py`는 1,131줄이다. 사람도 클로드도 그 크기에서는 한 번에 못 쥔다.

### References/ 를 처음부터 만들지 마라

조회 가이드 문서를 쓰고 싶어지면 **[03번](03-스키마.md)의 "스키마의 맹점을 DB 안에서 메운다"를 먼저 읽어라.** 어휘는 `SELECT DISTINCT`가, 허용값은 `CHECK`가, 관계는 FK가, 함정은 스키마 주석이 답한다. 그것들로 안 되는 것 — 여러 테이블을 가로지르는 조합 레시피 — 이 실제로 나왔을 때 그때 `References/조회레시피.md`를 만든다.

미리 만들면 대부분 스키마와 중복되고, **중복된 문서는 반드시 낡는다.** 그리고 낡은 쪽이 문서인지 스키마인지 알 방법이 없다.

## SKILL.md

### frontmatter

```yaml
---
name: congress
description: |
  대한민국 국회의 법률안·국회의원·회의록을 로컬 DB에 수집하고 그 위에서 SQL로 탐색한다.
  "국회", "법률안", "의안", "발의", "표결", "국회의원", "상임위", "회의록", "국정감사",
  "입법 동향", "법안 처리 현황"을 언급하거나, 특정 의원·법안·정책의 입법 경과를 확인해야 할 때 쓴다.
  국회 데이터를 찾는 일에는 WebSearch 대신 이 스킬을 쓴다 — WebSearch는 완결성을 보장하지 못해
  "발의한 법안 전부"나 "반대표를 던진 의원 명단" 같은 질문에 원리적으로 답할 수 없다.
  국회 OpenAPI도 쓰지 않는다 — 작동하지 않는 것이 많고 웹사이트와 값이 어긋난다.
  현행 법령 본문·판례·유권해석(법제처 소관)과 22대 이전 국회는 이 스킬의 범위가 아니다.
allowed-tools: Bash(uv run:*), Bash(sqlite3:*), Read, Glob, Grep
---
```

description을 이렇게 쓰는 이유: **트리거 어휘를 넓게 깔되 경계를 명시한다.** "국회"만 적으면 법제처 질문에도 뜨고, 너무 좁게 적으면 "이 법안 어떻게 됐어?"에 안 뜬다. 마지막 두 줄이 오발동을 막는다.

### 본문에 들어갈 것

News의 SKILL.md가 좋은 본보기다. **스키마가 이미 말하는 것을 반복하지 마라.** 본문의 값어치는 스키마가 답할 수 없는 것에 있다.

1. **이 스킬의 목적** — 조회 자동화가 아니라 국회를 아는 상태를 만드는 것. DB는 재료다.
2. **판단 원칙** — 수집은 완결성을, 조회는 선별성을. 누락 없음 > 중복 없음 > 속도.
3. **수집 도구 사용법** — 기본 실행이 정상 경로. 옵션은 `--help`로 넘긴다.
4. **완결성을 어떻게 읽나** — 불변조건 표와 각 값이 0이 아닐 때의 의미.
5. **SQL로 탐색하기** — 먼저 `.schema`를 읽으라고 지시하고, **스키마가 답할 수 없는 것만** 적는다:
   - FTS가 없으니 `LIKE`를 쓴다는 것과 그 이유
   - 발언 검색 시 회의·날짜·의원 인덱스로 먼저 좁히기
   - `bill_votes`에 행이 없는 것이 불참이 아니라는 것
   - 안건과 발언을 잇지 말 것
   - 대안반영폐기 계보를 따라가는 법
6. **데이터 경계** — 무엇이 없는지. 본회의 회의록, 조문 원문, 22대 이전.

**경로는 `{skill_dir}` 기준으로 쓴다.** 스킬을 로드하면 그 디렉터리를 알게 되므로 저장소 루트나 홈 기준 경로를 쓰지 않는다.

## 스크립트 CLI

인터페이스가 곧 문서다. **인자 이름과 제약이 잘못된 사용을 애초에 불가능하게 만든다.**

### `collect.py` — 유일한 공개 명령

```
uv run {skill_dir}/Scripts/collect.py            # 정상 경로: 따라잡기
uv run {skill_dir}/Scripts/collect.py --audit-only   # 상태만 본다. 락을 잡지 않는다
uv run {skill_dir}/Scripts/collect.py --backfill     # 22대 전체를 처음부터
uv run {skill_dir}/Scripts/collect.py --only bills|members|meetings
uv run {skill_dir}/Scripts/collect.py --retry all    # 상한 도달분 되살리기
uv run {skill_dir}/Scripts/collect.py --rate 4       # 초당 요청 수
```

**`--audit-only`가 락을 잡지 않는 것이 중요하다.** 수집이 도는 중에도 상태를 볼 수 있어야 하고, 그래야 "지금 뭐 하고 있나"를 묻는 데 비용이 안 든다.

기본 실행이 백필과 증분을 구분하지 않는다 — **같은 코드가 같은 판정(구멍이 있는가)을 하고 범위만 다르다.** 백필 전용 스크립트를 따로 만들면 둘이 어긋난다.

### `db.py` — 스키마와 원장

```
uv run {skill_dir}/Scripts/db.py init     --db …
uv run {skill_dir}/Scripts/db.py schema   --db …
uv run {skill_dir}/Scripts/db.py selftest --db /tmp/t.db
```

> ⚠️ **`selftest`는 `--db`를 필수 인자로 받아야 하고, 실제 `CONGRESS.db`를 지목하면 거부해야 한다.**
> selftest의 첫 동작이 대상 파일을 무조건 삭제하는 것이라, 기본값이 실제 DB인 채로 인자를 잊으면
> 수집물이 통째로 사라진다. News 프로젝트에서 실제로 그렇게 4.25GB를 잃었다 — 이름이 selftest라
> 안전할 것이라고 넘겨짚고 사용법을 읽지 않은 것이 전부였다.
> 그래서 경고 문구가 아니라 **인자 자체를 필수로** 만든다. 문서는 안 읽히지만 인자는 안 주면 실행이 안 된다.

`selftest`는 임시 DB에 스키마를 만들고 관계·제약·멱등성을 단언한다. 최소한 이것들:

- 테이블과 FK가 전부 존재한다
- `CHECK` 제약이 오타 상태값(`'찬성이'`, `'복회의'`)을 거부한다
- `members`에 없는 slug로 `bill_votes`를 넣으면 거부된다
- 같은 상세를 두 번 넣어도 `bill_stages` 행이 늘지 않는다
- `reason_text`를 받은 뒤 목록 정보만 다시 넣어도 본문이 보존된다 (REPLACE 금지의 회귀 테스트)
- 발의자 목록이 빈 응답으로 와도 기존 발의자가 지워지지 않는다
- 뷰가 없고 FTS 테이블이 없다

### 주석에도 회귀 테스트를 건다

특이하지만 값이 크다. **스키마 주석이 이 프로젝트의 1차 인터페이스인데, 주석은 코드처럼 조용히 퇴행한다.** 이전 프로젝트에서 마이그레이션 하나가 앞선 마이그레이션이 심어 둔 경고 문구를 **실수로 덮어써 사라지게 한 사고**가 실제로 있었고, 그 뒤로 "핵심 경고 키워드가 살아 있는가"를 CI에서 잠갔다.

우리는 DDL이 파일 하나에 있으니 더 쉽다. `selftest`가 `.schema` 출력을 문자열로 받아 확인한다:

| 어디에 | 살아 있어야 할 키워드 |
|---|---|
| `meeting_utterances` | `안건` (발언을 안건에 잇지 말라는 경고) |
| `bill_votes` | `불참` (행 없음 ≠ 불참) |
| `members.open_na_id` | `동명이인` |
| `bills.bill_id` | `영구키` |
| `committees` | `자동 등록` |

키워드 몇 개면 충분하다 — 문장 전체를 대조하면 문구를 다듬을 때마다 테스트가 깨져서 곧 무시하게 된다. **잠그는 것은 표현이 아니라 경고의 존재다.**

### `verify.py` — 원천이 바뀌었는지

`selftest`와 다른 질문에 답한다. selftest는 **우리 코드**의 회귀를 잡고, `verify.py`는 **국회 사이트**가 바뀌었는지를 실데이터로 본다. 알려진 의안·회의록 몇 건을 실제로 받아 기대한 필드가 여전히 나오는지 확인한다.

각 도구가 자기 `--help`에 무엇을 단언하는지 적어라.

## GitHub Actions

News 저장소의 두 워크플로를 본떠 만든다(`.tmp/Naver-News/.github/workflows/`). **그 파일들의 주석까지 읽어라** — 왜 self-hosted인지, 왜 워치독이 따로 있는지가 거기 적혀 있고 같은 이유가 여기에도 적용된다.

**`scheduled-collect.yml`** — `runs-on: self-hosted`, 하루 1회 새벽(KST). DB가 로컬 파일이라 클라우드 러너에는 그 파일이 없다. GitHub은 크론·로그·알림만 맡고 실행은 맥이 한다.

**`collect-watchdog.yml`** — `runs-on: ubuntu-latest`. 감시 대상이 맥이므로 감시자는 맥 밖에 있어야 한다. 러너가 죽거나 맥이 하루 넘게 꺼져 있으면 예약 run이 24시간 큐 대기 후 *cancelled*로 사라지는데, **취소는 실패가 아니라서 알림이 가지 않는다.** 그래서 "아무 메일도 안 왔으니 잘 돌고 있나 보다"가 몇 주씩 이어질 수 있다.

`concurrency` 그룹으로 예약 run끼리 직렬화한다. 스크립트에도 파일 락이 있지만(손실행까지 막아야 하므로) 여기서 막으면 애초에 러너를 점유하지 않는다.
