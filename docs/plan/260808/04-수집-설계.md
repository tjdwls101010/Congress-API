# 수집 설계

## 우선순위는 이 순서로 고정된다

**누락 없음 > 중복 없음 > 속도.**

누락된 의안이나 회의록은 존재 자체를 알 수 없어 영원히 복구되지 않지만, 느린 수집은 그저 느릴 뿐이다. 이 순서를 뒤집고 싶어지는 순간이 반드시 오는데(백필이 지루할 때), 그때 이 문단을 다시 읽어라.

## 완결성을 어떻게 증명하나

도메인마다 증명 방식이 다르다. **각각이 "빠진 게 있는가"에 참/거짓으로 답할 수 있어야 한다.**

### 의안 — 번호 구멍 세기

의안번호가 연속 정수라는 실측(1000행 연속, 구멍 0)이 이걸 가능하게 한다. 원장도 커서도 필요 없다.

**숫자 의안번호만 대상이다.** `ZZ22124` 형식 88건은 번호 체계 밖이라 연속성 판정에서 뺀다.

```sql
-- 이 값이 0이 아니면 그 수만큼 누락이다.
WITH n AS (SELECT CAST(bill_no AS INTEGER) AS no FROM bills
           WHERE assembly_unit = 22 AND bill_no GLOB '[0-9]*')
SELECT (SELECT MAX(no) - MIN(no) + 1 FROM n) - (SELECT COUNT(*) FROM n);
```

구멍이 어디인지도 바로 나온다:

```sql
WITH n AS (SELECT CAST(bill_no AS INTEGER) AS no FROM bills
           WHERE assembly_unit = 22 AND bill_no GLOB '[0-9]*')
SELECT a.no + 1 AS gap_from FROM n a
WHERE NOT EXISTS (SELECT 1 FROM n b WHERE b.no = a.no + 1)
  AND a.no < (SELECT MAX(no) FROM n);
```

**하한은 확인됐다 — `2200001`이다**(전수 실측). 그래서 백필 직후의 `MIN`이 이 값이 아니면 그 자체가 누락 신호다.

### 의안 상세 — 안티조인

```sql
SELECT COUNT(*) FROM bills b
WHERE b.bill_kind = '법률안'
  AND b.detail_collected_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM collect_failures f
                  WHERE f.target_kind = 'bill_detail' AND f.target_key = CAST(b.bill_no AS TEXT));
```

**실패 원장을 빼는 것이 핵심이다.** 원천에 없는 의안(`gone`)까지 미수집으로 세면 이 값이 영영 0이 되지 않고, 매 실행이 실패로 보고되며, 사용자는 곧 경고를 무시하게 된다. **늘 빨간 신호는 신호가 아니다.**

### 회의록 — 발견과 수집의 안티조인

```sql
SELECT COUNT(*) FROM meetings m
WHERE m.committee_class <> '본회의'          -- 본회의는 본문 수집 범위 밖
  AND NOT EXISTS (SELECT 1 FROM meeting_utterances u WHERE u.conference_id = m.conference_id)
  AND NOT EXISTS (SELECT 1 FROM collect_failures f
                  WHERE f.target_kind = 'meeting_body'
                    AND f.target_key = CAST(m.conference_id AS TEXT));
```

이게 성립하려면 **`meetings`가 먼저 완전해야 한다.** 회의를 발견하는 경로는 둘이다:

1. 회의록 트리 (`sessCmit.do` → `cmit.do`) — 종류별로 전부 훑는다. **프로토콜이 실측 검증됐다**([02번](02-데이터-원천.md) 7절)
2. 의안 상세의 회의정보 링크 — 의안을 받다 보면 저절로 쌓인다. 트리가 놓친 회의를 잡는다

두 경로가 어긋나면 트리 쪽이 빠뜨린 것이다. 그 차이를 세는 것 자체가 감사다.

### 차수 연속성 — 트리를 신뢰하지 않고도 누락을 잡는다

이게 회의록 쪽의 진짜 완결성 장치다. 회의는 (위원회 × 회기 × 차수)로 유일하고 **차수는 1부터 연속**이므로, 의안번호와 같은 산술 검증이 성립한다.

```sql
-- 제3차가 있는데 제2차가 없다 → 누락이다
SELECT m.committee_name, m.session_no, m.sitting_no - 1 AS missing_sitting
FROM meetings m
WHERE m.sitting_no > 1
  AND NOT EXISTS (SELECT 1 FROM meetings p
                  WHERE p.committee_name = m.committee_name
                    AND p.session_no = m.session_no
                    AND p.sitting_no = m.sitting_no - 1);
```

**이 검증이 강한 이유는 목록이 아니라 수집한 본문의 메타에서 나오기 때문이다.** 트리가 빠뜨렸는지를 트리에 묻지 않고 판정할 수 있다 — 트리를 신뢰의 근거로 삼지 않는다는 뜻이다.

다만 **하한은 못 잡는다.** 제1차부터 통째로 빠진 (위원회, 회기)는 이 질의에 안 걸린다. 그건 회기 목록과 대조해야 하고, 회기 목록은 회의록검색 폼이 준다([02번](02-데이터-원천.md) 7절).

### 의원 — 총원 대조는 시드가 있을 때만 성립한다

**의원 도메인에는 산술 완결성 장치가 없다.** 의안번호나 차수 같은 연속 키가 없어서, "빠진 사람이 있는가"를 데이터 스스로 답하게 만들 수 없다.

권위 있는 총원을 주는 유일한 원천은 명부 JSON API의 `resultCnt`(299)인데 **그것이 막혀 있다**([07번](07-미해결-확인사항.md)). 그래서 이 대조는 조건부다.

- `members_seed.json`이 있으면 → `SELECT COUNT(*) FROM members WHERE is_incumbent = 1`이 시드의 `resultCnt`와 같아야 한다
- 없으면 → **이 항을 `skip`으로 표시한다. 빨간불이 아니다.** 판정할 근거가 없는 것과 판정에 실패한 것은 다르다

시드가 없을 때 남는 보증은 약하지만 유의미하다 — **표결·발의자·발언에서 만난 모든 slug가 `members`에 있고 프로필이 채워져 있다.** 22대 전 의원이 최소 한 번은 표결하거나 발의하거나 발언하므로 실질 커버리지는 높다. 다만 **"전원을 받았다"를 증명하지는 못한다.** 그 한계를 알고 쓰라 — 여기가 이 DB에서 완결성이 가장 약한 지점이다.

## 갱신 — 무엇이 변하고 무엇이 안 변하나

| 대상 | 변하나 | 갱신 방식 |
|---|---|---|
| 의안 목록(제목·제안일자·제안자) | 안 변함 | 새 번호만 추가 |
| **의안 심사진행상태·의결결과** | **상시 변함** | 매 실행 재확인 |
| **심사 단계(bill_stages)** | **추가됨** | 매 실행 재확인, 행 추가 |
| 제안이유 본문 | 안 변함 | 한 번 받으면 끝 |
| 표결 결과 | 확정 후 불변 | 한 번 받으면 끝 |
| 회의록 본문 | 확정 후 불변 | 한 번 받으면 끝 |
| **의원 프로필·정당** | **가끔 변함** (사퇴·재보궐·탈당) | 매 실행 전체 재확인. `members`의 모든 slug에 대해 상세 페이지를 다시 받는다(320건 안팎, 싸다) |

### 미처리 의안만 다시 보면 안 된다

"이미 처리된 의안은 안 변하니까 건너뛰자"는 유혹이 있는데, **처리된 뒤에도 단계가 더 붙는다.** 본회의 가결 → 정부이송 → 공포가 며칠~몇 주에 걸쳐 일어난다. 그리고 대통령 거부권이 오면 재의결로 또 바뀐다.

그래서 갱신 대상은 이렇게 잡는다:

- **공포까지 끝난 의안**만 확정으로 보고 건너뛴다
- 그 외 모든 법률안은 매 실행 상세를 다시 확인한다
- 다시 확인하는 비용이 부담되면 `bills.date_proposed` 최근 N개월 + `review_status`가 종결이 아닌 것으로 좁힌다 — 다만 **좁히는 순간 그 밖에서 일어난 변화를 놓친다**는 것을 알고 좁혀라

### 재실행은 멱등해야 한다

모든 쓰기가 `INSERT … ON CONFLICT DO UPDATE` 또는 `DO NOTHING`이다. **`INSERT OR REPLACE`를 절대 쓰지 마라** — REPLACE는 행을 지우고 다시 넣으므로 명시하지 않은 컬럼이 전부 기본값으로 돌아간다. 이미 받아 둔 `reason_text`가 조용히 지워지고, 중복 행이 안 생기니 겉보기엔 멀쩡하며, 증상은 "매 실행마다 전량을 다시 받는다"로만 나타나 성능 문제로 오진하기 쉽다.

`bill_stages`는 PK가 `(bill_no, stage, seq)`라서 같은 단계를 다시 봐도 덮어쓸 뿐이다. 그래서 **상세를 몇 번을 다시 받아도 안전하다.**

### 부분 실패가 조용히 데이터를 지우게 두지 마라

발의자·표결처럼 **목록 전체를 다시 받는 자식 테이블**을 갱신할 때 `DELETE 후 INSERT`가 자연스러워 보인다. 그러면 **파싱이 실패해 빈 목록이 돌아온 한 번이 그 의안의 발의자를 전멸시킨다.** 이전 프로젝트에서 실제로 일어난 사고다 — DELETE 범위가 너무 넓어서 빈 응답 하나에 발의자가 통째로 사라졌다.

웹 스크래핑은 API보다 이 위험이 크다. 응답이 200이면서 내용만 비어 있는 경우(팝업 파라미터가 바뀌었을 때 실제로 그랬다)가 흔하기 때문이다.

**규칙: 새로 받은 목록이 비어 있으면 지우지 말고 실패로 기록한다.** 비어 있는 것이 정상인 경우(정부제출 의안의 발의자)와 파싱 실패를 가르는 것은 `proposer_kind` 같은 **다른 근거**여야지, 빈 목록 자체여서는 안 된다.

## 트랜잭션 경계

한 의안의 상세 수집은 **한 트랜잭션이다**: `bills`의 상세 컬럼 + `bill_stages` + `bill_proposers` + `bill_meetings`(+ 표결이 있으면 `bill_vote_summary` + `bill_votes`), 그리고 **맨 마지막에 `detail_collected_at`**. 갈라지면 "상세는 있는데 발의자가 없는" 행이 생기고, 완결성 판정이 `detail_collected_at`만 보므로 **그 결손이 영원히 안 잡힌다.**

`detail_collected_at`을 트랜잭션의 **마지막에** 쓰는 것이 규율의 핵심이다. 먼저 쓰고 중간에 죽으면 완결 표시가 붙은 빈 의안이 생기고, 그 의안은 다시 수집되지 않는다.

같은 이유로 한 회의의 본문 수집도 한 트랜잭션이다: `meetings` + `meeting_speakers` + `meeting_utterances` + `meeting_agenda`.

## 순서 의존성

```
1. 의원 시드(있으면) ← members_seed.json. 없으면 이 단계를 건너뛴다
2. 의안 목록(전체)   ← 싸다. 21회 요청 · 1분
3. 회의록 트리       ← 70회 요청 · 30초 · 회의 2,056건
4. 회의록 본문       ← 2,056건 · 수십 분
5. 의안 상세·표결·발의자 (법률안만) ← 가장 비싸다. 수 시간
```

**이 순서는 FK가 아니라 비용이 정한다.** 4·5는 서로 독립이고, 싼 도메인을 먼저 끝내면 트랜잭션 경계·스텁·실패 원장·감사가 전부 한 번 완주된 상태에서 가장 비싼 것을 돌리게 된다.

**의원이 1번 자리를 잃은 이유:** 명부 API가 막혀서([07번](07-미해결-확인사항.md)) 시작 시점에 받을 수 있는 의원 목록이 없다. 대신 **표결·발의자·발언에서 slug를 만나는 그 자리에서 `members` 행을 만든다.** 그래서 `members`는 선행 단계가 아니라 다른 수집의 부산물로 자란다.

이것이 FK를 깨지 않는 이유는 **한 트랜잭션 안에서 참조되는 쪽을 먼저 쓰기 때문이다.** 발의자 13명을 넣기 전에 그 13개 slug의 `members` 행(없으면 스텁)을 먼저 만든다. 트랜잭션이 커밋되면 FK가 만족된 상태이고, 롤백되면 스텁도 함께 사라진다.

**어느 경우에도 slug를 버리지 마라.** 시드에 없는 사람(임기 중 사퇴한 전직 의원)을 만나는 것은 정상이고, 그때 행을 버리면 그 사람의 표결·발의·발언이 통째로 사라진다.

시드가 있으면 1번에서 현직 299명이 먼저 들어가므로 스텁이 거의 생기지 않고 `mona_cd`도 채워진다. 없으면 전원이 스텁으로 시작해 상세 페이지로 채워진다 — **결과 데이터는 `mona_cd`를 빼면 같다.**

### 스텁 행은 그 자리에서 최대한 채운다

조인이 안 끊기는 것만으로는 부족하다. **이름만 있고 정당이 NULL인 행은 "정당별 찬반 분포" 같은 질의에서 에러 없이 빠진다** — 행은 있는데 `GROUP BY party`가 NULL 버킷으로 몰아넣기 때문이다. 이전 프로젝트가 정확히 이렇게 당했다: 떠난 의원 20명의 정당이 NULL이라 공동발의 216,537행의 **5.2%**가 정당 집계에서 조용히 샜다.

그래서 스텁을 만들 때 **그 slug를 만난 자리에서 얻을 수 있는 것을 같이 넣는다.** 원천마다 주는 것이 다르다:

| slug를 만난 곳 | 함께 얻는 것 |
|---|---|
| 발의자 팝업 | 한글명 · 한자명 · **정당** |
| 회의록 `.man` | 이름 · 직위 · **지역구** |
| 표결 명단 | 이름뿐 — **여기서만 만난 의원이 가장 비어 있다** |

그다음 `/members/22nd/{slug}` 상세를 받아 나머지를 채운다. **떠난 의원도 이 페이지가 살아 있다**(전재수 의원으로 실측 확인) — 그래서 스텁이 이름만 남는 경우는 사실상 없다. 다만 전직 페이지에는 소속위원회·연락처가 없으므로 `member_committees`가 비는 것은 정상이다.

**빈 채로 남는 것을 감사가 보게 하라** — 아래 불변조건의 `members_missing_party`가 그 역할이다. 0이 아닌 것이 곧 실패는 아니지만, 그 수만큼 정당 기반 집계가 틀린다는 뜻이다.

**FK를 지키려고 데이터를 버리는 것이 가장 나쁘다.** 같은 규칙이 `committees`에도 적용된다: 모르는 위원회명을 만나면 거부하지 말고 먼저 UPSERT로 등록한 뒤 진행한다. FK의 목적은 **표기가 갈라지지 않게 하는 것**이지 새 값을 막는 것이 아니다.

그래서 어느 도메인이든 쓰기 순서는 **참조되는 쪽 먼저**다 — `committees` → `members` → 나머지. 한 트랜잭션 안에서도 이 순서를 지킨다.

## 실패 처리

`collect_failures`가 잔여물 원장이다. 성공하면 행이 삭제되므로 **비어 있는 것이 정상이다.**

`kind`는 둘뿐이다:

- **`retriable`** — 일시 실패. `attempts < 5`인 동안 재시도 큐에 남는다.
- **`gone`** — 원천에 없다(404 등). 재시도하지 않는 것이 정상이고, 실패로 세지 않는다.

**상한(5회)에 별도 상태값을 두지 않는다.** `attempts >= 5`라는 값 자체가 그 상태이고, `kind`와 `detail`이 그대로 남으므로 원인 정보를 잃지 않는다. 파서를 고쳤다면 리셋 플래그로 되살린다. 상한이 없으면 완결성 조건이 영영 성립하지 않아 매 실행이 실패로 보이고, 그러면 경고가 무시된다.

`detail`에 접두어를 붙여 다음 조치를 고르게 한다 — `network:`가 몰리면 전송 문제, `parse:`가 몰리면 DOM 변경이나 파서 결함이다.

## 성공은 종료 코드가 아니라 불변조건이다

수집 실행은 stdout에 JSON 요약을 낸다. 아래가 **동시에** 만족해야 정상이다.

| 불변조건 | 의미 |
|---|---|
| `bill_no_gaps == 0` | 의안번호에 구멍이 없다 |
| `bill_detail_missing == 0` | 법률안 중 `detail_collected_at`이 NULL인 것이 없다 (실패 원장 제외) |
| `meeting_bodies_missing == 0` | 수집 범위 회의 중 본문 미수집이 없다 (실패 원장 제외) |
| `sitting_gaps == 0` | (위원회 × 회기)의 차수가 1부터 연속이다 |
| `orphan_member_refs == 0` | 표결·발언·발의자의 slug가 전부 members에 있다 |
| `dangling_alt_bills == 0` | `alt_bill_id`가 가리키는 의안이 전부 있다 (백필 완료 후) |
| `orphan_bill_meetings == 0` | 본회의를 뺀 `bill_meetings`의 회의가 전부 `meetings`에 있다 |
| `unresolved_retriable == 0` | 상한 미달의 재시도 대상이 없다 |
| `incumbent_count == roster_count` | 현직 수가 명부 총원과 일치한다 |
| `members_total == 320` | 22대를 거쳐 간 인원 (현직 299 + 전직 21) |
| `members_missing_party` | 정당이 비어 있는 의원 수. **0이 아니면 그만큼 정당 집계가 틀린다** |
| `promulgated_without_number == 0` | 공포 단계가 있는데 공포번호·공포법률명이 빈 의안. **`billInfo.do`에 잘못된 form을 보내면 여기가 튄다** |

`gone_total`은 **실패 기준이 아니다.** 값이 튀면 파서나 원천 구조에 문제가 있다는 신호이지, 0이어야 하는 값이 아니다.

뒤의 두 줄은 FK를 일부러 안 건 자리를 대신 지킨다([03번](03-스키마.md)의 관계 지도 참조). FK가 없는 곳은 조용히 깨지므로 **감사가 유일한 방어선이다.**

위원회 표기가 갈라졌는지도 함께 본다 — FK가 값의 일치는 보장하지만 **비슷한 두 이름이 각각 등록되는 것은 못 막는다.**

```sql
-- 공백·중점만 다른 유사 중복. 0이 아니면 눈으로 확인한다
SELECT a.committee_name, b.committee_name FROM committees a JOIN committees b
  ON a.committee_name < b.committee_name
 WHERE replace(replace(replace(a.committee_name,' ',''),'·',''),'ㆍ','')
     = replace(replace(replace(b.committee_name,' ',''),'·',''),'ㆍ','');
```

**이 정규화로는 부족하다.** 이전 프로젝트 실측에서 회의록 위원회명 38종 중 의안 쪽과 정확히 일치한 것은 24종이었고, 공백을 제거해도 30종까지만 맞았다 — **8종(약 21%)이 남는다.** 남는 차이는 상임위 최상위 명칭이 아니라 **소위원회 이름**에 몰린다(`법안심사제1소위원회` vs `법안심사 제1소위원회` 같은 것).

그래서 `bill_stages`의 소위 단계와 `meetings`의 소위 회의를 `committee_name`으로 조인하면 **에러 없이 일부만 나온다.** 감사에 괄호 제거·접미사 비교를 더하고, 그래도 남는 쌍은 사람이 눈으로 확인하는 절차를 두어라. **자동으로 합치지는 마라** — 실제로 다른 소위일 수 있다.

## 속도 — 실측해서 정한다

사용자가 "실측해서 정한다"를 골랐다. **측정 없이 숫자를 박지 마라.**

절차:

1. 초당 2요청으로 의안 상세 200건을 받아 응답시간 중앙값·실패율을 기록한다
2. 4 → 6 → 8로 올리며 같은 것을 잰다
3. 실패율이 오르거나 응답시간 중앙값이 뚜렷이 나빠지는 지점 **바로 아래**를 기본값으로 삼는다
4. 그 값과 근거(실측 수치)를 스크립트의 `--help`와 SKILL.md에 적는다

기억할 것: **속도는 완결성 장치가 아니다.** 어떤 값을 고르든 데이터는 잃지 않는다 — 실패한 요청은 `collect_failures`가 받고 다음 패스가 회수한다. 그래서 속도 실험은 안전하다.

## 중단 복구

어디서 죽어도 다음 실행이 이어받는다. 근거는 완결성 판정이 **DB 상태만 보고** 이뤄진다는 것이다 — 커서도, 진행 파일도, 재개 지점도 저장하지 않는다. 다음 실행이 "구멍이 있는가"를 다시 물으면 그게 곧 남은 일 목록이다.

동시 실행은 하나만 허용한다(파일 락). 이미 돌고 있으면 **종료코드 0으로 빠진다 — 실패가 아니다.** 매 실행은 슬롯이 아니라 따라잡기여서 다음 실행이 이번 몫까지 가져간다.
