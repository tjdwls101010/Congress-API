# 04 — 수집과 갱신

## 1. 갱신 전략의 전환

### v2가 무엇을 했나

```sql
-- 상세 재수집 대상
detail_collected_at IS NULL
  OR detail_collected_at < updated_at
  OR (outcome = '계류' AND detail_collected_at < datetime('now','-30 day'))
```

세 갈래다. 그리고 각 갈래가 각자의 전제를 갖는다.

- **첫째**는 `detail_collected_at`이 상세 트랜잭션 커밋 시에만 채워진다는 것
- **둘째**는 `updated_at`이 **"목록 값이 실제로 바뀔 때만"** 밀린다는 것 — `ON CONFLICT DO UPDATE … WHERE bills.x IS NOT excluded.x` 라는 미묘한 규칙에 걸려 있고, `<>` 대신 `IS NOT`을 써야 NULL 변화를 잡는다. v1이 이 규칙을 어겨 전량 재수집을 부른 사고가 있었고 `selftest`에 그걸 지키는 테스트가 넷 있다
- **셋째**는 목록만으로 못 잡는 변화가 있다는 것을 인정한 보완이다 — 최악 30일

### v3이 하는 것

```sql
-- 상세 재수집 대상
WHERE outcome = '계류'
```

**끝이다.**

근거는 셋이다.

**① 종결된 의안은 안 바뀐다.** `공포`·`대안반영폐기`·`수정안반영폐기`·`철회`·`폐기`·`부결`은 되돌아가지 않는다.

> **계류 14,788건(72%)을 매번 받고 종결 5,831건(28%)은 안 받는다.** v2 대비 비용이 늘지만, 늘어난 만큼이 정확히 "낡을 수 있던 구간"이다.

**② 목록만으로는 소위 이동을 원리적으로 못 잡는다.** 법안이 소위에 회부돼도 `review_status`는 `소관위심사` 그대로다. 실측으로 소위 단계가 16,434행인데 목록 어디에도 소위를 말하는 값이 없다. 그래서 "목록이 바뀐 것만" 규칙은 **계류 법안의 진행을 볼 수 없다.**

**③ 조건문이 하나면 어긋날 곳이 없다.** `updated_at`의 미묘한 규칙도, `IS NOT` vs `<>`도, 30일 계산도 사라진다. `selftest`에서 관련 테스트 넷이 없어진다.

### 비용

| 대상 | 건수 | 요청/건 | 비고 |
|---|---|---|---|
| 목록 전체 | 20,619 | 21요청 총 | 1,000행/요청 · 1.9초 → 40초 |
| 계류 상세 | 14,788 | 1~2 | `billInfo.do` + (대안 있으면) `anBillInfo.do` |
| 의원 전원 | 323 | 1 | 몇 분 |
| 회의록 신규 | 하루 수~수십 | 1 | 트리 열거 + 본문 |

**계류 상세 재수집이 1.5~2시간.** v2의 전면 재수집이 2~3시간이었고 계류가 72%이므로 그 비율이다.

> **발의자 팝업은 계류 재수집에서 뺀다.** 발의자는 안 바뀐다(철회하면 의안 자체가 종결된다). 이게 비용의 상당 부분이다 — 191명짜리 의안은 14페이지를 받아야 한다.
>
> **표결도 뺀다.** 계류 의안은 본회의 표결이 없다. 표결이 생기는 순간 `outcome`이 종결로 바뀌므로 **그 마지막 한 번**에만 받으면 된다.

즉 계류 재수집의 실제 요청은 `billInfo.do` 하나 + 대안 관계가 있을 때 `anBillInfo.do` 하나다.

### 종결로 넘어가는 순간의 처리

계류 → 종결로 판정이 바뀌는 실행에서는 **전부 다시 받는다** (발의자·표결·대안·공포법률 포함). 그 뒤로는 안 받는다.

```
if 새 outcome != '계류' and 옛 outcome == '계류':
    표결·발의자·대안·공포법률까지 전부 수집
```

이게 이 설계의 유일한 조건 분기다.

## 2. `outcome` · `current_stage` 판정

**유도 규칙이 아니라 파싱이다.** 위젯을 읽는 것이 전부다.

```python
def parse_progress(tree) -> tuple[str | None, str, dict[str, str]]:
    """심사진행단계 위젯에서 (current_stage, outcome, 마일스톤 날짜들)을 읽는다.

    ⚠️ 위젯은 클라이언트가 그린다 — billDetailPage.do 의 HTML 에는 #insc-step-sect 가
       비어 있다. billInfo.do 응답을 파싱해야 한다.
    ⚠️ 단계 목록의 길이는 의안마다 다르다. 여섯 칸을 가정하지 마라.
    """
    steps = []
    for div in tree.css("#insc-step-sect > div[data-gbn]"):
        steps.append({
            "gbn":   div.attributes.get("data-gbn"),
            "label": text_of(div, ".title"),
            "date":  text_of(div, ".stepdate") or None,
        })

    dated = [s for s in steps if s["date"]]
    current_stage = dated[-1]["label"] if dated else None

    dcs = next((s for s in steps if s["gbn"] == "DCS"), None)
    milestones = {
        "date_transferred":      next((s["date"] for s in steps if s["gbn"] == "GOVTRANS"), None),
        "date_reexam_requested": next((s["date"] for s in steps if s["gbn"] == "REEXAM"), None),
        "date_promulgated":      dcs["date"] if dcs and dcs["label"] == "공포" else None,
    }
    return current_stage, (dcs["label"] if dcs and dcs["date"] else None), milestones
```

`outcome` 최종 결정은 **`alt_bill_no`가 정해진 뒤** 한다.

```python
def decide_outcome(dcs_label: str | None, alt_bill_no: str | None) -> str:
    if dcs_label:                # 위젯이 결말을 말했다
        return dcs_label
    if alt_bill_no:              # 대안에 흡수됐는데 그 대안이 아직 안 끝났다
        return "대안반영폐기"     # (v2 의 '본회의불부의' 319건)
    return "계류"
```

> ⚠️ **위젯이 안 주는 결말은 `alt_bill_no`뿐이다.** 실측으로 `본회의불부의` 319건 중 317건이 여기 걸리고, 나머지 2건은 대안 관계가 아직 안 들어온 것이다(그 대안이 다음 실행에 들어오면 해소된다). 감사가 `outcome='계류'인데 소관위 처리결과가 있는 의안` 같은 이상 신호를 볼 필요는 없다 — 대신 **`alt_bill_no`가 `bills`에 없는 행 수**를 센다.

> ⚠️ `dcs["label"] == "공포"`인데 날짜가 없는 것이 미종결의 표시다. `DCS` 칸은 진행 중일 때도 `공포`라는 라벨을 달고 나온다.

## 3. `alt_bill_no` 채우기

원천이 `anBillInfo.do`(대안정보 탭) 하나로 **양방향을 준다** — 의안 하나를 물으면 그것을 흡수한 대안 1건과 **같이 흡수된 형제 전부**(최대 246건)를 돌려준다.

v2는 형제 전부에 대해 행을 만들었고, 그 과정에서 **무관한 대안이 2건 섞였다**([D4](01-진단.md#d4)). v3의 규칙:

```
① 이 의안의 대안정보 탭이 있으면 → 거기 적힌 '대안'을 이 의안의 alt_bill_no 로 쓴다
② 그 응답의 형제 목록에 있는 의안들에 대해서는 → alt_bill_no 를 **이 응답의 대안으로만** 채운다
   (즉 형제의 alt_bill_no = 지금 보고 있는 대안. 다른 값으로 덮지 않는다)
③ 이미 값이 있으면 덮어쓰지 않는다 — 자기 페이지에서 온 값이 언제나 이긴다
```

> ⚠️ 원천 템플릿이 라벨을 이렇게 가른다: `refIdCount > 0 ? '대안반영폐기 의안 (N건)' : '대안'`.
>
> ⚠️ **본회의불부의 상태의 의안은 대안정보 탭이 아예 없다**(실측 `TABS: []`). 그 의안의 `alt_bill_no`는 ②번 경로로만 온다. 대안은 원안보다 번호가 크므로 같은 목록 패스 안에서 반드시 뒤에 온다 — 순서 의존이지만 깨지지 않는다.

**감사 게이트**: `SELECT COUNT(*) FROM bills b WHERE b.alt_bill_no IS NOT NULL AND NOT EXISTS(SELECT 1 FROM bills x WHERE x.bill_no = b.alt_bill_no)` 이 0이어야 한다.

## 4. `committees` 채우기의 변화

**`committee_class`가 사라졌으므로 `upsert_committee`가 단순해진다.**

```python
def upsert_committee(db, name: str, *, parent: str | None = None) -> str:
    """모르는 위원회명을 만나면 거부하지 말고 먼저 등록한다. **실제로 저장된 표기를 돌려준다.**"""
    if parent:
        parent = upsert_committee(db, parent)      # 자기참조 FK — 상위를 먼저
    # 공백·중점만 다른 기존 행이 있으면 그 표기를 쓴다
    if row := db.execute(
            "SELECT committee_name FROM committees WHERE "
            "replace(replace(replace(committee_name,' ',''),'·',''),'ㆍ','') = "
            "replace(replace(replace(?,' ',''),'·',''),'ㆍ','')", (name,)).fetchone():
        name = row[0]
    db.execute("""INSERT INTO committees (committee_name, parent_committee) VALUES (?, ?)
                  ON CONFLICT(committee_name) DO UPDATE SET
                      parent_committee = COALESCE(excluded.parent_committee, parent_committee)""",
               (name, parent))
    return name
```

> `first_seen_at`이 없어져 "먼저 본 표기가 이긴다"는 규칙이 "정규화 비교에서 먼저 찾힌 표기가 이긴다"로 바뀐다. **어느 쪽이 옳은지 판정할 근거가 원천에 없으므로**(likms '기후위기 특별위원회' / record '기후위기특별위원회' 둘 다 그 사이트의 정식 표기다) 옳음이 아니라 **하나로 모으는 것**만 보장하면 된다.
>
> `consolidate_committees`는 유지한다 — `upsert_committee`는 새로 갈라지는 것만 막고, 이미 두 행이 되어 있으면 각자 자식을 거느린 채 남는다.
