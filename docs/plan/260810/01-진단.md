## D1 — `outcome`이 공포된 법안을 `계류`로 판정한다

```sql
SELECT bill_no, review_status, decision_result, outcome, date_promulgated
FROM bills WHERE date_promulgated IS NOT NULL AND outcome <> '공포';
```

```
2200851 | 재의(가결) | 수정가결 | 계류 | 2025-04-22
```

**2200851은 대통령이 거부권을 쓴 뒤 본회의가 재의결해 법이 된 법안이다.** 원천의 심사진행단계도 `DCS:공포(2025-04-22)`로 끝난다. 그런데 `derive_outcome()`이 `review_status='재의(가결)'`를 아는 값 목록에 넣지 않아 마지막 `return '계류'`로 떨어뜨렸다.

`db.py`의 주석이 이걸 예고하고 있었다.

> 모르는 값은 `'계류'`로 떨어진다. … 국회는 새 상태 문자열을 예고 없이 늘린다. 그래서 떨어뜨리되 감사의 `DISTINCT review_status` 추이가 새 값의 등장을 잡는다.

**설계대로 동작한 것이지만, 잡는 장치가 사람이 감사표를 읽는 것뿐이라 실제로는 안 잡혔다.** 유도 규칙을 없애는 것이 v3의 답이다.

부수 확인 — `재의` 계열 전체:

```sql
SELECT review_status, outcome, COUNT(*) n, SUM(date_promulgated IS NOT NULL) 공포일있음
FROM bills WHERE review_status LIKE '재의%' GROUP BY 1,2;
```

```
재의(가결) | 계류     |  1 | 1     ← D1
재의(부결) | 재의부결 | 26 | 0
재의요구   | 계류     |  1 | 0     ← 아직 진행 중. 맞다
```

## D3 — `date_decided`·`decision_result`가 `bill_stages`와 완전 중복이다

       SUM(s.date_processed IS NOT NULL) stage_has,
       SUM(b.date_decided IS NOT NULL AND s.date_processed IS NULL) only_bills,
       SUM(b.date_decided IS NOT NULL AND s.date_processed IS NOT NULL
           AND b.date_decided <> s.date_processed) mismatch

  ON s.bill_no=b.bill_no AND s.stage='본회의' AND s.seq=1;

## D5 — `committees.committee_class`가 위원회가 아니라 회의의 종류를 담는다

```sql
SELECT committee_class, COUNT(*) n FROM committees WHERE parent_committee IS NULL GROUP BY 1;
```

```
국정감사 16 · 특별위원회 15 · 국정조사 5 · 상임위원회 3 · (빈값) 3 · 예산결산특별위원회 1
```

**상임위원회가 3개뿐이다.** 실제로는 17개 안팎인데, 14개가 `국정감사`로 분류돼 있다.

```
국정감사 :: 과학기술정보방송통신위원회
국정감사 :: 교육위원회
국정감사 :: 법제사법위원회
상임위원회 :: 보건복지위원회      ← 국정감사를 안 연 셋만 살아남았다
```

**원인은 회의록 트리의 `class_id_sch`를 그대로 위원회에 되먹인 것이다.** 그 값은 다섯인데(2 상임위 / 3 특위 / 4 예결위 / 5 국정감사 / 6 국정조사) 앞의 셋은 *위원회가 무엇인가*이고 뒤의 둘은 *회의가 무엇인가*다. 국정감사는 상임위별로 열리므로 같은 위원회가 두 섹션에 나타나고, `upsert_committee`의 `COALESCE`가 **먼저 본 쪽을 고정**한다.

```sql
SELECT committee_name, GROUP_CONCAT(DISTINCT committee_class)
FROM meetings GROUP BY 1 HAVING COUNT(DISTINCT committee_class) > 1;
```

```
과학기술정보방송통신위원회 | 상임위원회,국정감사
교육위원회                 | 상임위원회,국정감사
…
```

부수로 `국회본회의`가 `특별위원회`로, `본회의`가 빈값으로 들어와 **같은 것이 두 행**이다. 그리고 `순직 해병 … 진상규명을 위한 국정조사특별위원회` / `진실규명을 위한 …` 두 행이 공존한다(원천의 오타로 보인다).

## D10 — 진행/결말 어휘가 넷이다

| 컬럼 | 값 수 | 예시 |
|---|---|---|
| `review_status` | 18 | 소관위심사 · 소관위접수 · 본회의부의안건 · 재의(부결) |

넷을 잇는 규칙이 `derive_outcome()`(파이썬)과 감사의 SQL `CASE` 두 벌에 나뉘어 있고, `selftest`가 540가지 조합으로 둘을 대조한다. **대조 장치가 필요하다는 것 자체가 중복의 증거다.**

그리고 값들의 관계가 자명하지 않다. 예를 들어 `본회의불부의`(319건)와 `대안반영폐기`(3,839건)는 이름이 전혀 달라 보이지만 실측하면 같은 운명의 두 시점이다.

SELECT b.outcome 원안결말, ab.outcome 대안결말, COUNT(*) n
FROM bill_alternatives a JOIN bills b ON b.bill_no=a.bill_no
LEFT JOIN bills ab ON ab.bill_no=a.alt_bill_no GROUP BY 1,2;

## D12 — 표결 명단이 요약보다 1명 적은 것이 61건

```sql
SELECT COUNT(*) 요약행, SUM(v.yes+v.no+v.abstain = c.n) 명단일치
FROM bill_vote_summary v LEFT JOIN (SELECT bill_no, COUNT(*) n FROM bill_votes GROUP BY 1) c USING(bill_no);
```

```
요약행 1,656 · 명단일치 1,595   (불일치 61건, 전부 정확히 1명 부족)
```

`collect_failures`가 이유를 적고 있다: `gone:slug 없는 표 1건 (동명이인)`. **22대에 박지원이 둘이라**(`PARKJIEWON` 5선 전남 / `PARKJIWON` 초선 전북) 이름만 주는 표결 명단에서 가를 수 없다.

**이건 우리 결함이 아니라 원천의 한계다.** 고칠 수 없으므로 주석에 못 박고 감사에서는 보고값으로 둔다.

## D13 — 갱신이 최악 30일 낡을 수 있다

v2 설계(`260809/03-갱신-설계.md`)의 재수집 조건:

```sql
detail_collected_at IS NULL
  OR detail_collected_at < updated_at
  OR (outcome = '계류' AND detail_collected_at < datetime('now','-30 day'))
```

세 갈래다. 그리고 **둘째 갈래는 `updated_at`이 "값이 진짜 바뀔 때만 밀린다"는 규칙에 의존한다** — v1이 그 규칙을 어겨 전량 재수집을 부른 사고가 이미 있었고(`db.py:989`의 경고), `selftest`에 그걸 지키는 테스트가 넷 있다.

셋째 갈래가 필요한 이유는 **목록만으로는 소위 이동을 못 잡기 때문**이다.

```sql
SELECT COUNT(*) 소위행, SUM(date_referred IS NOT NULL AND date_processed IS NULL) 소위계류
FROM bill_stages WHERE stage='소위';
```

```
소위행 16,434 · 소위계류 11,140
```

법안이 소위에 회부돼도 `review_status`는 `소관위심사` 그대로다. 그래서 "목록이 바뀐 것만"으로는 계류 법안의 진행을 원리적으로 놓치고, 30일 주기는 그 구멍을 **막은 것이 아니라 30일짜리로 줄인 것**이다.
