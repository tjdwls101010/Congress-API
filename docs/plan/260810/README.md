# congress 스킬 v3 계획 — 2026-08-10

v2 스키마를 테이블 하나·필드 하나씩 다시 따져 **꼭 필요한 것만 남기고, 남은 것끼리 명확히 연결되게** 다시 설계한 계획이다. **이 세션은 계획만 세웠고 코드는 한 줄도 고치지 않았다.** 구현은 다음 세션이 이 문서를 읽고 한다.

## 왜 v3인가

v2는 동작한다. 의안 20,619건·회의록 2,047건·발언 138만 행이 들어와 있고 의안번호에 구멍이 0이다. **문제는 같은 사실을 여러 컬럼이 서로 다른 어휘로 말한다는 것이다.**

"이 법안 결국 어떻게 됐나"에 답하는 컬럼이 v2에 넷 있다 — `review_status`(18종)·`decision_result`(7종)·`outcome`(9종)·`bill_stages.result`(15종). 넷이 서로 다른 어휘를 쓰고, 넷 사이를 잇는 규칙이 `derive_outcome()`이라는 파이썬 함수와 그것을 SQL로 옮겨 적은 감사 질의 두 곳에 나뉘어 있다. 조회하는 클로드는 매번 "어느 컬럼을 봐야 하나"를 판단해야 하고, 그 판단이 틀려도 에러가 안 난다.

**그리고 실제로 틀려 있었다.** 2200851은 대통령 거부권 뒤 재의결로 법이 된 법안인데(공포 2025-04-22) `outcome`이 `계류`다. `derive_outcome()`이 `review_status='재의(가결)'`를 모르는 값으로 보고 조용히 떨어뜨렸다.

v3의 답은 **원천이 이미 정본 어휘를 준다**는 것이다. 의안 상세 페이지의 `심사진행단계` 위젯이 그것이고, 그 값을 그대로 저장하면 유도 규칙이 사라진다. 유도 규칙이 없으면 유도 버그도 없다.

## 이 계획을 관통하는 원칙

**① 원천이 말한 것을 저장하고, 유도하지 않는다.**

v2는 `review_status`·`decision_result`·`bill_stages.result` 셋에서 `outcome`을 계산했다. 계산하는 곳이 파이썬 함수와 SQL 두 벌이라 둘이 갈릴 수 있었고, 새 상태 문자열이 나오면 조용히 `계류`로 떨어졌다. v3은 위젯의 라벨을 그대로 넣는다 — **웹페이지를 열어 눈으로 대조할 수 있는 값**이 된다.

**② 유도 가능한 것은 지운다. 단 "유도 가능"은 실측으로 증명한다.**

`date_decided`·`decision_result`는 `bill_stages(본회의)`와 5,885건이 일치하고 불일치가 0이라 지웠다. `bill_promulgated_laws`는 반대다 — 99.2%가 1:1이지만 11건이 법률 2~10개를 공포하므로 컬럼으로 접히지 않는다. **비율이 아니라 "접히지 않는 경우가 있는가"가 기준이다.**

**③ 컬럼 하나를 지우는 판단은 "무엇을 못 묻게 되나"로 한다.**

`bill_stages`의 처리결과를 지우기로 했을 때 본회의불부의 319건의 판정 근거가 사라지는 것을 확인하고, 그 자리에 `alt_bill_no` 기반 규칙을 넣었다. 지우기 전에 **지워도 답할 수 있는지를 먼저 확인한다.**

**④ 완결성은 조건문이 하나일 때만 지켜진다.**

v2의 상세 재수집 조건은 세 갈래(`detail_collected_at IS NULL` · `< updated_at` · `계류 AND 30일 경과`)였고, 첫 갈래는 `updated_at`이 "값이 진짜 바뀔 때만 밀린다"는 미묘한 규칙에 의존했다. v3은 `WHERE outcome='계류'` 한 줄이다.

## 이 계획이 목표하지 않는 것

**모든 정보를 담지 않는다.** 상정일·문서 링크(검토보고서 PDF)·관련위 심사정보·본회의 회의록은 원천에 있지만 담지 않기로 했다. 지엽적인 것을 담아 늘어나는 복잡도가 본질을 흐리기 때문이고, 이 DB의 본질은 **"법률안이 어디까지 왔고, 그 과정의 회의에서 무슨 말이 오갔나"**다.
