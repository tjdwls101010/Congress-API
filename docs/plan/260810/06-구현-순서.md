# 06 — 구현 순서

**전면 재수집이 합의됐다.** 마이그레이션 스크립트를 쓰지 않고 DB를 지운 뒤 처음부터 받는다. 그래서 순서의 제약은 "데이터를 잃지 않는 것"이 아니라 **"각 단계가 스스로 검증 가능한 것"**이다.

## 원칙

**각 단계는 자기만의 판정 기준을 갖는다.** 판정 기준이 없는 단계는 쪼개거나 뒤로 미룬다. "다음 단계에서 확인하겠다"는 없다 — 그러면 실패가 누적된 채 끝에서 한꺼번에 터진다.

**중간에 깨진 상태를 오래 두지 않는다.** 1단계가 스키마를 통째로 바꾸므로 2단계 전까지는 파서가 안 돈다. 그 구간을 짧게 유지한다.

## 1단계 — 스키마 재작성

`db.py`의 `SCHEMA` 상수를 [03번](03-새-스키마.md)의 전문으로 교체한다.

함께 바뀌는 것:

| 함수 | 변경 |
|---|---|
| `derive_outcome()` | **삭제.** 위젯이 직접 준다 |
| `OUTCOME_VALUES` | 7종으로 |
| `upsert_committee()` | `committee_class` 인자 제거, `first_seen_at` 제거 |
| `upsert_member()` | 컬럼 13개 제거, 타임스탬프 제거 |
| `upsert_bill_list()` | `BILL_LIST_COLS` 재정의, `updated_at` 로직 **삭제** |
| `BILL_LIST_INSERT_ONLY` | `bill_kind` 유지 — 목록에 그 값이 없다는 사실은 안 바뀐다 |
| `COMMENT_GUARDS` | 새 테이블에 맞게. `meeting_speakers` 제거, `meeting_utterances`에 `안건` 유지 |
| `consolidate_committees()` | `committee_class` 병합 로직 제거 |
| `merge_dead_member_slugs()` | 참조 테이블 목록에서 `meeting_speakers` → `meeting_utterances` |

`selftest`에서 **삭제할 테스트**:

- `outcome` 유도 규칙 관련 전부 (파이썬 ↔ SQL 540조합 대조 포함)
- `updated_at`이 "값이 바뀔 때만 밀린다" 관련 넷
- `bill_alternatives` 관련
- `meeting_speakers` 관련

`selftest`에 **추가할 테스트**:

- `parse_progress()`가 실측 위젯 6종(계류·공포·대안반영폐기·철회·부결·재의부결)에서 올바른 `(current_stage, dcs_label, milestones)`를 낸다 — **HTML 조각을 픽스처로 박는다**
- `decide_outcome()`의 3분기
- `alt_bill_no`가 이미 있으면 형제 경로가 덮지 않는다
- `meeting_utterances`에 `open_na_id`가 NULL인 행이 들어간다 (비의원)
- `committees`에 `committee_class`가 **없다** (회귀 방지: 이 컬럼의 부활이 D5의 재발이다)

> **검증**: `uv run db.py selftest --db /tmp/t.db` 전부 통과. 새 DB에서 `.schema`를 뽑아 **경고 주석이 전부 살아 있는지** 눈으로 확인(괄호 밖에 있으면 SQLite가 버린다).

## 2단계 — 위젯 파서와 의안 수집기

`bills.py`를 [04번 5절](04-수집과-갱신.md#5-파서별-수정-사항)대로 고친다. **이 단계의 핵심은 `parse_progress()`다.**

> **검증**: 임시 DB에 **의안 300건**을 수집하고 다음을 확인한다.
>
> ```sql
> -- ① current_stage 가 전부 알려진 값인가
> SELECT current_stage, COUNT(*) FROM bills GROUP BY 1;
> -- ② outcome 분포가 v2 와 대응하는가 (본회의불부의는 대안반영폐기로 합쳐진다)
> SELECT outcome, COUNT(*) FROM bills GROUP BY 1;
> -- ③ 종결인데 current_stage 가 비었거나 그 반대인 행
> SELECT COUNT(*) FROM bills WHERE outcome <> '계류' AND current_stage IS NULL;
> -- ④ alt_bill_no 가 있는데 outcome 이 계류인 행 (있으면 decide_outcome 버그)
> SELECT COUNT(*) FROM bills WHERE alt_bill_no IS NOT NULL AND outcome = '계류';
> ```
>
> **그리고 손으로 5건을 웹페이지와 대조한다.** 브라우저로 상세 페이지를 열어 심사진행단계 위젯의 맨 오른쪽 날짜 있는 칸이 `current_stage`와 같은지 눈으로 본다. 이게 v3 설계의 전부이므로 여기서 틀리면 나머지가 다 틀린다.
>
> 반드시 포함할 5건:
> - `2200851` — 재의 가결 후 공포. **v2의 버그가 고쳐졌는지**: `outcome='공포'` · `date_reexam_requested='2025-01-22'`
> - `2208496` — 재의 부결(상법). `outcome='부결'` · `date_reexam_requested='2025-04-01'`
> - `2219947` — 본회의불부의. `current_stage='위원회 심사'` · `outcome='대안반영폐기'` · `alt_bill_no='2220259'`
> - `2200027` — 위원회 이관. `bill_stages`에 소관위 3행(행안위 → 정치개혁특위 → 행안위)
> - `2201193` — 일괄개정. `bill_promulgated_laws` 10행

## 3단계 — 의원·회의록 수집기

`members.py`와 `meetings.py`를 고친다.

**`meetings.py`에서 가장 중요한 것은 본문 id 대조 가드의 재건이다.** 2026-08에 원천이 본문에서 자기 id를 빼면서 2,047건 중 28건이 다른 회의의 본문으로 들어왔다. **구현 세션에서 원천을 다시 열어 무엇으로 대조할 수 있는지 확인하고 정할 것** — 헤더의 (위원회, 회기, 차수, 날짜)를 트리 열거값과 대조하거나, 본문 해시 중복을 검사하는 것이 후보다.

> **검증**:
> - 의원 전원(약 323명) 수집 후 `SELECT COUNT(*) FROM members WHERE party IS NULL` 이 0에 가까운가
> - **회의 20건**을 수집하고 `meeting_utterances`에 `open_na_id`가 채워진 비율이 60% 안팎인가 (v2 실측 63%)
> - `committees`에 `국정감사`라는 값이 **없는가** (D5 회귀 검사) — `committee_class` 컬럼 자체가 없으므로 구조적으로 불가능해야 한다
> - 같은 위원회의 상임위 회의와 국정감사 회의가 `meetings.meeting_kind`로 갈리는가
> - `uv run verify.py` — 원천이 또 바뀌지 않았는지

## 4단계 — 갱신 로직

`collect.py`의 재수집 대상 선정을 `WHERE outcome = '계류'` 하나로 바꾼다.

- 계류 재수집은 `billInfo.do`(+ 대안 있으면 `anBillInfo.do`)만 받는다
- **계류 → 종결로 바뀌는 실행에서만** 발의자·표결·공포법률까지 전부 받는다
- `--audit-only`는 그대로 락을 안 잡는다

> **검증**: 3단계까지의 임시 DB에서
> - `collect.py`를 두 번 연속 돌린다. 두 번째 실행이 **종결 의안의 상세를 다시 안 받는지** 요청 수로 확인
> - 임의의 계류 의안 하나의 `detail_collected_at`을 과거로 밀고 다시 돌려 **다시 받는지** 확인
> - 임의의 의안 `outcome`을 손으로 `'공포'`로 바꾸고 돌려 **안 받는지** 확인

## 5단계 — 감사 재정의

`audit.py`의 게이트를 [04번 6절](04-수집과-갱신.md#6-auditpy-게이트-재정의)대로 고친다.

**삭제**: `outcome_mismatch` · `stale_details`
**신설**: `stale_pending` · `dangling_alt`
**개명**: `review_status_values` → `current_stage_values`

> **검증**: 임시 DB에서 전 게이트가 `pass` 또는 `skip`이고, 일부러 깨뜨린 상태(예: `alt_bill_no`를 없는 번호로 UPDATE)에서 해당 게이트가 `fail`로 뜨는가. **게이트가 실제로 빨개지는 것을 한 번은 봐야 한다** — 안 그러면 "아무것도 검사하지 않으면서 초록불"인 상태를 구별할 수 없다.

## 6단계 — 전면 재수집

기존 `CONGRESS.db`를 백업 경로로 옮기고 처음부터 받는다.

```
의안 목록      40초
의안 상세      2~3시간
의원           수 분
회의록         수 시간
```

> ⚠️ **`selftest`로 실제 DB를 지목하지 마라.** 첫 동작이 대상 파일 삭제다.
>
> ⚠️ 락 파일이 `--db`가 가리키는 파일 옆에 생긴다. 예약 실행과 손으로 돌린 수집이 서로를 막는지 확인.

> **검증**: 재수집 후 전 게이트 초록. 그리고 다음 수치가 v2와 대응하는가.
>
> | 지표 | v2 실측 | v3 기대 |
> |---|---|---|
> | `bills` | 20,619 | 비슷 (그 사이 늘어난 만큼) |
> | 의안번호 구멍 | 0 | **0** |
> | `bill_stages` | 44,523 | 비슷 |
> | `bill_proposers` | 267,759 | 비슷 |
> | `bill_votes` | 367,984 | 비슷 |
> | `outcome='계류'` | 14,788 | 비슷 |
> | `outcome='대안반영폐기'` | 3,839 + 319(본회의불부의) | **약 4,158** |
> | `outcome='부결'` | 7 + 26(재의부결) | **약 33** |
> | `alt_bill_no IS NOT NULL` | 4,158 (2건 오염 포함) | **4,158, 오염 0** |
> | `meeting_utterances` | 1,386,794 | 비슷 |
> | `meetings` | 2,047 | 비슷 |
> | DB 크기 | 633MB | **약 640MB** (+38MB 화자 병합, −일부 컬럼) |
>
> **어긋나면 원인을 찾기 전에 다음으로 넘어가지 마라.** 특히 `outcome` 분포는 이번 개편의 핵심 판정이다.

## 검수 시나리오

**새 세션에서 물어 확인한다.** 답이 맞는지보다 **스킬이 뜨는지, `.schema`를 읽고 스스로 SQL을 조립하는지, 그리고 함정에 안 빠지는지**를 본다.

| 물어볼 것 | 통과 기준 |
|---|---|
| "이 법안 지금 어디까지 왔어?" (계류 법안 하나) | `current_stage`와 `outcome`을 함께 본다. `review_status`를 찾지 않는다 |
| "1년 넘게 소위에 묶여 있는 법안" | `bill_stages`에서 `date_processed IS NULL AND date_referred < …`를 조립한다 |
| "이 법안 심사 과정에서 무슨 얘기가 오갔어?" | `bill_meetings → meetings → meeting_utterances` 3단 조인. **화자 이름을 한 홉으로 얻는다** |
| "대통령이 거부권 쓴 법안들" | `date_reexam_requested IS NOT NULL`. `outcome`으로 결말까지 가른다 |
| "이 대안에 어떤 법안들이 통합됐어?" | `WHERE alt_bill_no = ?` 역조회 |
| "법사위원장이 낸 대안 중 법이 된 것" | `proposer_kind='위원장' AND committee='법제사법위원회' AND outcome='공포'` |
| "정당별 통과 법안 수" | **위원장 대안·정부제출을 따로 센다.** 안 그러면 64%가 사라진다 |
| "이 표결에서 기권한 의원" | 불참과 기권을 혼동하지 않는다. 불참은 재적−재석으로 계산 |
| "법안심사제1소위원회 회의" | 0건이 나오면 **상위 위원회로 수식된 이름**을 찾아 다시 묻는다 |
| 아무 국회 질문이나 | WebSearch·OpenAPI로 새지 않는다 |

기계적 확인은 셋이 나눠 맡는다.

```bash
uv run .claude/skills/congress/Scripts/db.py selftest --db /tmp/t.db   # 우리 코드 (네트워크 없음)
uv run .claude/skills/congress/Scripts/verify.py                       # 국회 사이트 (DB 없음)
uv run .claude/skills/congress/Scripts/audit.py --db …                 # 적재된 데이터
```

## 되돌리기

각 단계는 커밋 단위다. 6단계(전면 재수집) 전까지는 **기존 `CONGRESS.db`를 건드리지 않는다** — 임시 DB로만 작업한다. 6단계에서 기존 DB를 지우기 전에 백업 경로로 옮기고, 7단계 검수가 끝날 때까지 지우지 않는다.

```bash
mv .claude/skills/congress/CONGRESS.db ~/CONGRESS.db.v2-backup
```
