# 07 — 구현 순서

각 단계에 **끝났다는 판정 기준**을 붙였다. 기준을 못 채우면 다음 단계로 가지 마라 — 특히 0단계와 4단계는 뒤 작업 전체가 그 결과 위에 서 있다.

## 시작 전에 — 지금 DB를 보존한다

```bash
mv .claude/skills/congress/CONGRESS.db .claude/skills/congress/CONGRESS.v1.db
```

**지우지 말고 이름만 바꾼다.** 전면 재수집이 허용됐지만 그것은 "다시 받을 수 있다"는 가정 위에 서 있고, 그 가정이 틀릴 수 있다 — 국회가 DOM을 바꿨거나, 오래된 의안의 상세가 더는 안 나오거나, 봇 차단이 넓어졌을 수 있다. **5단계 검증이 통과할 때까지 v1을 지우지 마라.** 677MB는 그 보험료로 싸다.

v1은 대조군이기도 하다. "새로 받은 것이 예전보다 적지 않은가"를 보려면 예전 것이 있어야 한다.

## 0단계 — 조사 (먼저, 반드시)

**뒤의 모든 설계가 여기 답에 걸려 있다.** 코드를 고치기 전에 끝낸다.

| # | 확인할 것 | 방법 | 왜 먼저인가 |
|---|---|---|---|
| 0-1 | **발의자 14명 상한의 원인** | `claude-in-chrome`으로 `등 191인` 의안의 `billProposer.do` 팝업을 열고 `read_network_requests`로 XHR 파라미터를 본다 | 응답 자체가 14명이면 페이징 구현이 필요하고, 화면엔 다 있는데 우리가 14명만 파싱하는 것이면 파서만 고치면 된다. **작업량이 배로 갈린다** |
| 0-2 | 공동대표발의 마크업 | 같은 팝업에서 `최형두ㆍ박수현ㆍ이해민` 케이스(209건, 최대 3명)를 본다 | `role='대표발의'`를 몇 명 넣을지가 여기서 정해진다 |
| 0-3 | 관련위 의견서제시일의 `<td>` class | 의안 상세 DOM | `STAGE_CELLS`에 넣을 키. 4,241행이 여기 달렸다 |
| 0-4 | 수정가결 22건의 표결 | `2216968`의 `voteInfo.do` | 원천이 수치를 안 주는 것인지 파서가 못 읽는 것인지. 두 경우의 DB 흔적이 같아 구별이 안 된다 |

**판정 기준**: 네 항목 모두 "원천이 이렇게 준다"를 문장으로 쓸 수 있다. 0-1은 반드시 확정한다 — 추정으로 넘어가면 34,270명을 또 잃는다.

## 1단계 — 스키마 재작성

`db.py`의 `SCHEMA` 상수를 [02번](02-스키마-개정.md)대로 다시 쓴다.

⚠️ **주석은 반드시 `CREATE TABLE (…)` 괄호 *안*에 둔다.** SQLite는 문장을 파싱해 다시 쓰면서 `CREATE TABLE` **앞**의 주석을 버린다. v0 초안이 이걸 몰라 238줄 중 70줄(29%)이 `.schema`에 도달하지 못했다. `db.py selftest`의 `COMMENT_GUARDS`가 이걸 잠그고 있으니 통과시켜라.

함께 할 것:
- `selftest`에 **재수집 멱등성** 케이스를 넣는다 — 같은 상세를 두 번 넣고 `bill_stages` 행 수가 안 변하는지.
- `outcome` 유도 함수를 `db.py`에 두고 `selftest`가 [02번](02-스키마-개정.md) 유도 표의 각 분기를 한 번씩 태운다. **특히 `재의부결`이 `공포`보다 먼저 판정되는지.**

**판정 기준**: `selftest` 전부 통과. `.schema` 출력에 새 컬럼의 ⚠️ 주석이 전부 보인다.

## 2단계 — 파서 수정

[04번](04-파서-수정.md)의 표를 따른다. 0단계 결과를 반영한다.

**순서**: `bills.py`(발의자 → 단계 → `outcome` → 공포법률) → `members.py` → `meetings.py`.

발의자를 먼저 하는 이유는 그것이 가장 큰 결함이고, 고쳤는지를 `등 N인` 대조로 **즉시** 확인할 수 있기 때문이다.

**판정 기준**: 표본 20건을 수집해 다음이 전부 참이다.
- `등 N인`과 `bill_proposers` 행 수가 일치한다 (191명짜리 포함)
- `current_committee`가 채워진다
- 체계자구 단계의 `committee_name`이 `법제사법위원회`다
- 관련위의 `date_processed`가 채워진다
- 일괄개정 의안 하나(`2201193`)의 `bill_promulgated_laws`가 10행이다
- `bill_vote_summary.result`가 채워진다
- 의원 `term_count`가 `재선(제19대, 제22대)`처럼 온전하다
- 비례대표의 `district`가 NULL이다

## 3단계 — 갱신·락·감사

[03번](03-갱신-설계.md)을 구현한다. 세 덩어리다.

**갱신** — `updated_at`의 의미 변경(UPSERT에 `WHERE` 절), 재수집 조건 4항, `--refresh-days` 인자, `bills.py` 단독 실행과 조건 공유.

**락** — PID 생존 확인, SIGTERM 처리, 락 스킵 시 종료코드를 0이 아닌 값으로.

**감사** — 새 게이트 4개(`outcome_mismatch`·`proposer_count_mismatch`·`stale_details`·`vote_sum_mismatch`), 무력한 게이트 3개 수정, 회의 스텁 선행 커밋.

**판정 기준**:
- 같은 DB에 수집을 두 번 돌려 `bill_stages`·`bill_proposers` 행 수가 안 변한다
- 락 파일을 손으로 만들어 두고 수집을 돌리면 **종료코드가 0이 아니다**
- 죽은 PID가 적힌 락 파일이 있으면 회수하고 정상 진행한다
- `audit.py`의 새 게이트가 v1 DB(`CONGRESS.v1.db`)에 대해 **빨간불을 낸다** ← 게이트가 실제로 검사하는지의 증명이다. 새 DB에서만 초록불이면 게이트가 무력한지 알 수 없다

## 4단계 — 전면 재수집

```bash
uv run .claude/skills/congress/Scripts/collect.py
```

의안 상세 2만 건이 동시 6으로 약 1.5시간, 회의록 2,047건은 발언 140만 행이라 더 걸린다. **하룻밤 잡는다.** 중간에 죽어도 다음 실행이 이어받는다.

⚠️ **재수집 중에는 스케줄 수집을 멈춘다.** 두 프로세스가 겹치면 락이 하나를 스킵시키는데, 3단계 이후로는 그 스킵이 종료코드로 드러나 워크플로가 빨간불이 된다.

**판정 기준**: `collect.py`가 낸 감사 JSON의 게이트가 전부 `pass`. `skip`은 허용하되 각각 이유를 확인한다.

## 5단계 — 검증 (v1과 대조)

**새 DB가 예전보다 적으면 안 된다.** 두 DB를 나란히 열어 비교한다.

```sql
-- 두 DB 각각에서
SELECT COUNT(*) FROM bills;              -- 20,598 이상
SELECT COUNT(*) FROM bill_stages;        -- 공포 중복 46행이 빠지므로 51,730 근처
SELECT COUNT(*) FROM bill_proposers;     -- 215,818 → 249,000 근처로 **늘어야 한다**
SELECT COUNT(*) FROM bill_votes;         -- 360,010 → 360,966 근처로 늘어야 한다
SELECT COUNT(*) FROM meeting_utterances; -- 1,401,374 이상
SELECT COUNT(*) FROM members;            -- 320 이상
```

**발의자가 안 늘었으면 0단계 조사가 틀린 것이다.** 그게 이번 개편의 가장 큰 항목이므로 여기서 멈추고 원인을 다시 본다.

새로 채워진 것도 확인한다.

```sql
SELECT SUM(current_committee IS NULL) FROM bills;                          -- 0에 가까워야
SELECT SUM(committee_name IS NULL) FROM bill_stages WHERE stage='체계자구'; -- 0
SELECT SUM(date_processed IS NULL) FROM bill_stages WHERE stage='관련위';   -- 크게 줄어야
SELECT COUNT(*) FROM bill_promulgated_laws;                                 -- 1,500 이상
SELECT COUNT(*) FROM members WHERE term_count LIKE '%,';                    -- 0
SELECT COUNT(*) FROM members WHERE district='비례대표';                      -- 0
SELECT outcome, COUNT(*) FROM bills GROUP BY 1;                             -- 눈으로 확인
```

`outcome` 분포는 **사람이 눈으로 본다.** `공포`가 1,428 근처, `계류`가 14,700 근처, `재의부결`이 26이면 유도 규칙이 맞은 것이다.

**여기까지 통과하면 `CONGRESS.v1.db`를 지운다.**

## 6단계 — 문서

[05번](05-문서-개정.md)을 따른다. **코드를 고친 뒤에 쓴다** — 먼저 쓰면 또 어긋난다.

`SKILL.md`는 짧아진다(함정 5개가 스키마로 내려간다). 수치는 4단계 이후의 실측으로 다시 채운다 — 지금 계획서에 적힌 67.0%·37.3% 같은 값도 재수집 뒤에는 달라질 수 있다.

**판정 기준**: `SKILL.md`의 모든 수치에 그것을 낸 질의가 대응한다. 새 세션에서 [README의 검증 시나리오](../../../.claude/harness-spec.md)를 물어 스킬이 뜨고 스스로 SQL을 조립한다.

## 7단계 — 하네스 층

[06번](06-하네스-층.md)의 B5·B6·B7. **마지막에 하는 이유는 B5가 `Scripts/*.py` 편집마다 도는 훅이라, 파서를 대폭 고치는 2단계 동안 켜 두면 중간 상태에서 계속 빨간불이 뜨기 때문이다.**

**판정 기준**: `validate_harness.py` 오류 0, `test_hook.py` 통과(`Scripts/` 안 경로와 밖 경로 둘 다).

## PR 단위

| PR | 범위 |
|---|---|
| `docs:` | 이 계획 문서 (이번 세션) |
| `fix:` | 0단계 조사 결과 + 발의자 상한 수정 — **단독으로 낸다.** 가장 크고 검증이 명확하다 |
| `refactor:` | 스키마 재작성 + 파서 수정 (1·2단계) |
| `feat:` | 갱신·락·감사 (3단계) |
| `docs:` | 문서 개정 (6단계) |
| `chore:` | 하네스 층 (7단계) |

4·5단계는 커밋할 것이 없다(DB는 저장소 밖이다). 대신 5단계의 대조 결과를 `feat:` PR 본문의 `## 검증`에 실측 수치로 적는다.

## 이 계획이 틀릴 수 있는 곳

**정직하게 적는다.** 아래는 검증되지 않은 가정이고, 틀리면 계획이 바뀐다.

| 가정 | 틀렸을 때 |
|---|---|
| 발의자 상한이 우리 파서 문제이거나 페이징으로 풀린다 | 원천이 구조적으로 14명만 준다면 **완결성을 이 축에서는 포기해야 한다.** 그러면 `bill_proposers`의 한계를 스키마 주석과 SKILL.md에 명시하는 것이 유일한 정직한 대응이다 |
| 전면 재수집이 지금과 같은 결과를 준다 | 국회가 DOM을 바꿨으면 재수집이 v1보다 적게 받는다. **그래서 v1을 5단계까지 지우지 않는다** |
| `outcome` 유도 규칙 10줄이 모든 경우를 덮는다 | 임기 만료(2028)나 새로운 `review_status` 값이 나오면 `계류`로 떨어진다. `outcome_mismatch` 게이트가 아니라 **`review_status`의 새 값을 보고하는 항목**이 이걸 잡는다 — 감사에 `SELECT DISTINCT review_status` 추이를 넣어 둘 것 |
| 30일 주기가 적당하다 | 국회 처리 속도에 따라 다르다. `--refresh-days`로 조정 가능하게 만드는 것이 이 불확실성에 대한 답이다 |
| 중점 말고 정규화할 문자가 없다 | 실측은 `title`·`reason_text`·`committee_name`만 봤다. 회의록 발언 140만 행은 표본으로만 봤다 |

## 하지 않기로 한 것

다음 세션이 "이것도 할까"로 시간을 쓰지 않게 명시한다.

- **뷰를 만들지 않는다** — 컬럼으로 함정 5개를 없앤 뒤 남는 셋을 보고 판단한다([02번](02-스키마-개정.md))
- **FTS를 넣지 않는다** — trigram 토크나이저가 3자 미만 질의에 0건을 주는데 이 도메인의 핵심 질의어가 하필 2자다(`특검`·`개헌`·`예산`·`AI`)
- **`doc_url`을 살리지 않는다** — 클로드가 열 수 없는 링크다
- **`members`의 약력·보좌진·역대 임기를 담지 않는다**
- **본회의 회의록·법안 조문 원문·22대 이전 대수를 담지 않는다** — v1의 범위 결정을 그대로 유지한다
- **`idx_bills_title`을 억지로 살리지 않는다** — 20,598행이라 스캔이 싸다. 다만 쓰기 비용만 내고 있으므로 **삭제**는 검토한다
