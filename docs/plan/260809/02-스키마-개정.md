# 02 — 스키마 개정

**전면 재수집이 허용됐으므로 마이그레이션 스크립트를 쓰지 않는다.** `db.py`의 `SCHEMA` 상수를 새로 쓰고 DB를 지운 뒤 처음부터 받는다. 컬럼 이름·타입·제약을 자유롭게 고칠 수 있다는 뜻이다.

`bills`가 24컬럼에서 **17컬럼**으로, `members`가 19에서 **15컬럼**으로 줄어든다. 테이블은 12개에서 13개가 된다.

## 왜 `decision_result`를 지우고 `outcome`을 만드는가

`decision_result`는 두 가지 이유로 지운다.

**첫째, 완전히 유도 가능하다.** `bill_stages`(stage='본회의', seq=1)의 `result`와 20,598건 중 20,597건이 일치한다(예외는 본회의 단계가 없는 철회 1건).

**둘째, 이름이 거짓말을 한다.** 값에 두 종류가 섞여 있다 — 본회의 의결 결과(원안가결·수정가결·부결)와 본회의 의결이 아닌 종결 사유(대안반영폐기 3,839·철회 165·수정안반영폐기 39·폐기 10). 대안반영폐기는 위원회에서 대안에 흡수돼 사라진 것이지 본회의가 의결한 것이 아니다.

그 자리에 **"결국 어떻게 됐나"를 답하는 컬럼 하나**를 넣는다. 컬럼 수는 그대로인데 SKILL.md의 함정 세 개가 사라진다.

```sql
outcome  TEXT NOT NULL
         CHECK (outcome IN ('계류','공포','가결_미공포','부결','재의부결',
                            '대안반영폐기','수정안반영폐기','철회','폐기',
                            '본회의불부의','임기만료폐기')),
```

**유도 규칙 — 위에서부터 먼저 맞는 것을 쓴다(순서가 중요하다).**

| 순서 | 조건 | `outcome` |
|---|---|---|
| 1 | `review_status = '재의(부결)'` | `재의부결` |
| 2 | 공포 단계가 있다 **또는** `review_status='공포'` | `공포` |
| 3 | `review_status IN ('철회')` 또는 어느 단계든 `result='철회'` | `철회` |
| 4 | `review_status='대안반영폐기'` **또는** 어느 단계든 `result='대안반영폐기'` | `대안반영폐기` |
| 5 | `review_status='수정안반영폐기'` 또는 단계 result 동일 | `수정안반영폐기` |
| 6 | `review_status='본회의불부의'` | `본회의불부의` |
| 7 | 본회의 단계 `result='부결'` | `부결` |
| 8 | 본회의 단계 `result IN ('원안가결','수정가결')` | `가결_미공포` |
| 9 | `review_status='폐기'` 또는 단계 result `'폐기'` | `폐기` |
| 10 | 그 외 | `계류` |

**4번이 `review_status`만 보지 않고 단계까지 보는 것이 핵심이다.** 본회의에 못 올라가고 소관위에서 대안에 흡수된 원안이 511건 있는데, `review_status`만 보면 그 511건을 놓친다.

**1번이 2번보다 먼저인 것도 핵심이다.** 재의에서 부결된 26건은 본회의 원표결이 `원안가결`로 남아 있어, 순서를 바꾸면 통과로 잘못 센다(실측: 상법 2208496).

> `outcome`은 저장 컬럼이지 생성 컬럼이 아니다 — `bill_stages`를 참조하므로 SQLite의 `GENERATED ALWAYS AS`로는 표현할 수 없다(생성 컬럼은 같은 행만 참조한다). **상세를 받을 때마다 다시 계산해 쓴다.** 그래서 [03번](03-갱신-설계.md)의 갱신 설계가 이 컬럼의 정확성을 좌우한다.

**감사 불변조건을 함께 만든다.** `outcome`이 `bill_stages`에서 유도된 값이므로 둘이 어긋날 수 있고, 어긋나면 아무도 모른다. `audit.py`에 "저장된 `outcome` ≠ 지금 다시 계산한 `outcome`" 게이트를 추가한다 — v1에 없던 것은 이 감시 장치 하나뿐이다.

## `review_status`는 왜 남기나

`outcome`과 **독립적인 축**이기 때문이다. 교차표가 증명한다.

```
공포        / 원안가결   949      같은 결말, 다른 원표결
공포        / 수정가결   479
정부이송    / 원안가결    37      같은 원표결, 다른 위치
본회의의결  / 원안가결   261
```

`review_status`는 **어디까지 왔나**(18종의 세밀한 위치)이고 `outcome`은 **결국 어떻게 됐나**(11종의 결말)다. 계류 중인 14,780건을 "소관위접수 / 소관위심사 / 소관위심사보고 / 체계자구심사 / 본회의부의안건"으로 가르는 것은 `review_status`만 할 수 있다.

## `bills` 새 정의

```sql
CREATE TABLE bills (
    -- 22대에 제출된 모든 의안. 법률안뿐 아니라 예산안·결의안·동의안·규칙안까지.
    -- 왜 전체를 담나: 의안번호가 종류 구분 없이 연속된 정수라서, 전체를 담아야
    -- "번호에 구멍이 없다 = 누락이 없다"가 성립한다.
    bill_no          TEXT PRIMARY KEY,
                     -- '2214631'. 'ZZ22124' 형식이 88건 있어 INTEGER가 아니라 TEXT다.
    bill_id          TEXT NOT NULL UNIQUE,
                     -- 'PRC_…' 20,128건 · 'ARC_…' 470건. 'PRC_'만 가정하면 470건이 사라진다.
    assembly_unit    INTEGER NOT NULL,
    bill_kind        TEXT NOT NULL,           -- '법률안'|'예산안'|'결의안'|…
    title            TEXT NOT NULL,
                     -- ⚠️ 중점은 수집 시 '·'(U+00B7)로 정규화한다. 원천은 'ㆍ'(U+318D)를
                     --    462건에서 쓰는데 둘은 눈으로 구분되지 않아 LIKE가 조용히 0건이 된다.

    -- ── 발의자 ────────────────────────────────────────────────
    proposer_kind    TEXT CHECK (proposer_kind IN ('의원','위원장','정부','의장','기타')),
                     -- ⚠️ v1 주석은 셋만 적었으나 실제 값은 다섯이다('의장' 56건).
    proposer_org     TEXT,
                     -- 의원 발의가 아닐 때의 주체. '과학기술정보방송통신위원장' · '정부' · '의장'.
                     -- ⚠️ proposer_kind='의원'이면 NULL이고 신원은 bill_proposers가 정본이다.
                     --    그 반대도 참이다 — 위원장·정부·의장·기타 1,654건은 bill_proposers에
                     --    행이 아예 없다. 그래서 이 컬럼이 없으면 "어느 위원회의 위원장인가"를
                     --    답할 방법이 어디에도 없다(v1이 그랬다).

    -- ── 진행과 결말 ──────────────────────────────────────────
    date_proposed    TEXT,
    date_decided     TEXT,
    review_status    TEXT,                    -- 현재 위치. 18종. 원천 값 그대로.
    outcome          TEXT NOT NULL
                     CHECK (outcome IN ('계류','공포','가결_미공포','부결','재의부결',
                                        '대안반영폐기','수정안반영폐기','철회','폐기',
                                        '본회의불부의','임기만료폐기')),
                     -- **"결국 어떻게 됐나"는 이 컬럼 하나로 끝난다.**
                     -- review_status(위치)와 bill_stages(사건)에서 유도한 투영이다.
                     -- 통과한 법 = outcome='공포'. 계류 = outcome='계류'.
                     -- ⚠️ 유도 순서가 규칙이다(02번 문서의 표). 특히 '재의부결'을 '공포'보다
                     --    먼저 판정해야 한다 — 거부권 뒤 부결된 26건은 본회의 원표결이
                     --    '원안가결'로 남아 있어, 순서를 바꾸면 통과로 잘못 센다.
                     -- ⚠️ '대안반영폐기'는 bill_stages.result도 함께 봐야 한다. 본회의에
                     --    못 올라가고 소관위에서 흡수된 원안이 511건이다.
                     -- audit.py가 매 실행 이 값을 다시 계산해 대조한다.

    -- ── 상세 페이지에서만 오는 것 ────────────────────────────
    current_committee TEXT REFERENCES committees(committee_name),
                     -- **현재** 소관위원회. bill_stages(stage='소관위')의 가장 최근 행에서 유도.
                     -- ⚠️ 이름이 'current'인 이유: 소관위가 바뀌는 의안이 366건 있다.
                     --    2200027은 행안위 → 정치개혁특위 → 행안위로 두 번 옮겼다.
                     --    **이력은 bill_stages가 갖는다.** 여기는 지금 어디 소속인지만 말한다.
    proposal_session INTEGER,                 -- 418 (제418회)
                     -- ⚠️ 정수다. 원천은 '제22대(2024~2028)제418회'로 주는데 앞부분이
                     --    20,598행 전부 동일해 담을 값이 없다. 실제 값은 25종뿐이다.
    reason_text      TEXT,                    -- 제안이유 및 주요내용 (평문)
                     -- ⚠️ NULL을 '상세 미수집'의 판정자로 쓰지 마라 — 원래 비어 있는 의안이
                     --    있고, 그러면 매 실행이 자기를 다시 받는다. 판정자는 detail_collected_at이다.
    alt_bill_id      TEXT,                    -- 대안반영폐기 시 내용을 흡수한 법률안의 bill_id.
                     -- FK를 걸지 않는다 — 전방 참조이고, 원천이 의안 아닌 문서를 가리키는
                     -- 경우가 섞여 있다(실측 241건 미해소, audit이 보고값으로 추적).

    -- ── 수집 메타 ────────────────────────────────────────────
    collected_at     TEXT NOT NULL,           -- 목록 행을 처음 본 시각
    updated_at       TEXT NOT NULL,
                     -- ⚠️ **목록 값이 실제로 바뀐 시각이다.** "마지막으로 확인한 시각"이 아니다.
                     --    UPSERT의 DO UPDATE에 WHERE 절을 달아 값이 하나라도 다를 때만 쓴다.
                     --    이 정의가 갱신 트리거의 절반이다 — 03번 문서 참조.
    detail_collected_at TEXT
                     -- 상세를 **마지막으로** 받은 시각. NULL이면 한 번도 안 받았다.
                     -- 상세 트랜잭션(상세+단계+발의자+표결+공포법률)이 커밋될 때만 쓰므로,
                     -- 값이 있다는 것은 그 전부가 들어왔다는 뜻이다. 중단 후 재개가 여기 걸려 있다.
                     -- ⚠️ detail_collected_at < updated_at 이면 "목록이 바뀌었는데 상세가 낡았다"다.
);
```

## `bill_promulgated_laws` — 신설

**원천 페이지를 직접 열어 확인했다.** 공포정보 표는 `공포일자 · 공포번호 · 공포법률` 세 칸이고, 일괄개정법률안은 **행마다 다른 법률명**을 준다.

```
2201193  자치입법권 강화…농어촌정비법 등 10개 법률의 일부개정에 관한 법률안
  2024-12-20 | 20581 | 농어촌정비법
  2024-12-20 | 20581 | 도시농업의 육성 및 지원에 관한 법률
  2024-12-20 | 20581 | 도시숲 등의 조성 및 관리에 관한 법률
  …
  2024-12-20 | 20581 | 축산법
```

v1의 파서는 이 열 행을 모두 읽지만 `extra["promulgated_law_name"]`에 덮어써서 **마지막 하나(`축산법`)만 남긴다.** 그래서 `2201193`이 "축산법을 공포한 의안"으로 보인다 — 열 개 중 하나일 뿐인데.

```sql
CREATE TABLE bill_promulgated_laws (
    -- 이 의안으로 공포된 법률. **일괄개정법률안 때문에 의안당 여러 행이다.**
    --
    -- 왜 bills의 컬럼이 아닌가: 한 의안이 법률 여러 개를 동시에 개정하는 일괄개정법률안이
    -- 53건 있고, 원천이 공포정보 표에서 법률마다 한 행을 준다(실측 최대 18개).
    -- 컬럼 하나로 접으면 나머지를 잃고, 남은 하나가 대표성도 없다.
    bill_no    TEXT NOT NULL REFERENCES bills(bill_no) ON DELETE CASCADE,
    seq        INTEGER NOT NULL,             -- 공포정보 표의 행 순서
    law_name   TEXT NOT NULL,
               -- 공포된 법률의 이름. ⚠️ **의안명과 다르다** — 전부개정이면 이름 자체가 바뀐다.
               --    저출산·고령사회기본법 전부개정법률안 → 인구전략기본법
               --    진로교육법 일부개정법률안           → 평생교육법
               --    실측 1,425건 중 53건이 제목에서 유도 불가능하다.
               -- **"인구전략기본법이 언제 생겼나"는 bills.title 검색으로 답할 수 없다.**
               -- 바깥 자료(법제처 등)와 이름으로 맞출 때는 반드시 이쪽을 쓴다.
    ref_no     TEXT,                          -- 공포번호. 같은 의안의 여러 법률이 공유할 수 있다.
    date_promulgated TEXT,
    PRIMARY KEY (bill_no, seq)
);
CREATE INDEX idx_promulgated_law ON bill_promulgated_laws(law_name);
```

## `bill_stages` 변경

```sql
    doc_url          TEXT,     -- ← 삭제
```

**지우는 이유는 "못 채워서"가 아니라 "채워도 못 써서"다.** 원천에 링크는 실재한다(검토보고서·심사보고서). 다만 ⓐ `onclick="Navigation.bill.popup…"` JS 팝업이라 URL을 얻으려면 스크립트를 역해석해야 하고, ⓑ 대상이 HWP/PDF인데 이 스킬은 문서 본문을 수집하지 않으며, ⓒ `allowed-tools`에 `WebFetch`가 없어 클로드가 링크를 열 수도 없다. **열 수 없는 링크를 51,776행에 저장하는 것은 비용만 있고 이득이 없다.**

**나머지 셋은 채우거나 주석으로 못 박는다.**

```sql
    committee_name   TEXT REFERENCES committees(committee_name),
                     -- 소관위·소위·관련위 단계의 위원회. 본회의·정부이송·공포는 NULL.
                     -- ⚠️ **체계자구 단계는 언제나 '법제사법위원회'다.** 원천 표에는 위원회 칸이
                     --    아예 없고 캡션이 '법사위 체계자구 심사정보'로 말한다. 수집기가 상수로
                     --    넣는다 — 안 넣으면 committee_name='법제사법위원회'로 조회할 때
                     --    소관위 1,850건·관련위 295건은 잡히는데 체계자구 1,501건만 통째로 빠진다.
                     -- ⚠️ **소위는 원천이 절반만 준다**(실측 16,432행 중 8,642행이 빈 문자열).
                     --    파싱 실패가 아니라 소위 미배정 상태다. 어느 소위인지는 모르지만
                     --    어느 위원회의 소위인지는 같은 의안의 소관위 단계가 답한다.
    date_processed   TEXT,
                     -- 처리일. ⚠️ **단계마다 원천의 이름이 다르다** —
                     --    소관위·소위·체계자구는 '처리일', 본회의는 '의결일',
                     --    정부이송은 '정부이송일', 공포는 '공포일자',
                     --    **관련위는 '의견서제시일'이다**(v1이 이 하나를 매핑에서 빠뜨려
                     --    관련위 4,241행이 전부 NULL이었다).
    result           TEXT,
                     -- ⚠️ **관련위 단계에는 처리결과 칸이 원천에 없다.** NULL이 정상이고
                     --    파싱 실패가 아니다. 원천 표의 칸은 관련위원회·회부일·상정일·의견서제시일·문서다.
```

**공포 단계의 `seq` 부여 규칙을 바꾼다.** v1은 공포정보 표의 행마다 단계를 만들어 `2201193`에 구분 불가능한 중복행 10개를 만들었다. **공포 단계는 `(공포일자, 공포번호)` 고유 조합당 한 행이다** — 법률명은 `bill_promulgated_laws`가 담는다. 실측상 대부분 1행이 되고, 공포번호가 실제로 둘인 3건만 2행으로 남는다.

## `bill_vote_summary` — 생성 컬럼 하나

```sql
    absent  INTEGER GENERATED ALWAYS AS (total_seats - present) VIRTUAL,
            -- 불참자 수. **저장하지 않고 조회 때 계산한다.**
            -- ⚠️ 이 컬럼이 있는 이유: bill_votes에 행이 없는 것은 불참이 아니다.
            --    원천이 찬성·반대·기권 명단만 주고 불참자 명단은 주지 않는다.
            --    불참을 명단으로 유도하려는 시도를 이 컬럼 하나가 막는다.
```

`GENERATED ALWAYS AS … VIRTUAL`은 저장 공간을 쓰지 않고 `.schema` 출력에 그대로 나타난다. **SKILL.md의 프로즈 경고 하나가 스키마 안으로 들어간다.**

`result` 컬럼은 유지하되 **파서가 실제로 채우게 고친다** — v1은 INSERT 아홉 번째 자리에 리터럴 `None`이 박혀 있어 1,624건 전부 NULL이었다.

## 텍스트 정규화 — 중점 하나뿐

실측으로 확인한 변종은 **중점 하나뿐**이다. 나머지 후보는 전부 0건이었다(가타카나중점 U+30FB · 불릿 U+2022 · NBSP · 전각물결 · 전각괄호 · 대시).

```
수집 시: 'ㆍ'(U+318D, 한글 아래아)  →  '·'(U+00B7, 가운뎃점)
적용 대상: title · reason_text · committee_name · law_name · 그 밖의 모든 텍스트 컬럼
```

`·`로 모으는 이유는 공포법률명과 위원회명이 이미 `·`만 쓰기 때문이다. 원문 보존용 컬럼은 두지 않는다 — 두 표기의 차이가 의미를 담지 않고, 원천이 일관성 없이 섞어 쓸 뿐이다.

## 뷰는 이번에 만들지 않는다

`outcome`·`absent`·`current_committee`·`proposer_org`가 생기면 SKILL.md의 함정 8개 중 5개가 **컬럼으로** 사라진다. 남는 셋은 조인의 성질이라 컬럼으로 표현할 수 없다.

- `bill_proposers`만 조인하면 가결 법안의 67%가 사라진다 — *"이 테이블에 이 법안 행이 없다"*를 표현할 컬럼은 존재할 수 없다
- `bill_stages`는 언제나 LEFT JOIN
- 안건과 발언을 잇지 마라 — **없는 데이터**에 대한 경고이고, 스키마는 없는 것을 표현하지 못한다

셋뿐이라면 프로즈로 충분하다. **뷰를 만들면 같은 테이블에 두 번째 이름이 생기고 "어느 쪽을 쓰나"라는 새 판단이 매번 붙는다.** 컬럼으로 먼저 없애고 남은 것을 보자는 순서를 지킨다 — v2를 써 보고도 이 셋이 계속 사고를 내면 그때 뷰를 판단한다.
